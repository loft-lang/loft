## In progress: `@FR-R-DeferredCopy` (opt-in, `LOFT_DEFERRED_COPY=1`)

Owner asked for it after the analysis: the self-host interpreter (`selfhost/src/run.loft` on
`91-self-host`) spends ~46 % in `loft_copy_claims`: `prog = callee_prog` deep-copies a whole
`Lowering` per interpreted call ((B-Copy): a whole-value bind copies).  Module
`src/c/body/deferred.rs`, runtime `loft_dc_remap` in `loft_rt.h`, rule text in
`doc/claude/formal/rewrites.md` (R-DeferredCopy).  The bind takes the source's reference and
raises `loft_dcv<x>`; before each statement that may write a store not apart from the source's
(`call_writes_store` + `StoreFacts::distinct`, or two owners this activation created —
minted or placed — whose RECORDS are disjoint) the copy is taken if the flag is up; derived
views (`op = prog.ops[pc]`) are remapped into the copy (`loft_dc_remap`), held addresses
re-derived.  No copy point where the local and its views are dead after the statement, or
before the first deferred bind (`dead_after`).

Measured on the REAL self-host interpreter (scratch merge, see below), fib(25):
gcc 151 → 71 ms, clang 92 → 36 ms, same answer (75025); instructions −55 % (fib 18).

**The open problem — why it is opt-in:** under gcc, `mix` and `collatz` (few calls) run ~30 %
SLOWER with the rule on, though no copy point on their path ever runs.  Isolated: removing
only the `op = loft_dc_remap(…)` line (one remap of the hottest derived view at the copy point
in `Call`, where `op.b` is read after the lowering) restores the speed (mix: on 128 ms,
without the op remap 97, off 95; without the temp's remap 103).  `LOFT_UNLIKELY` on the flag
test does not help.  So a conditional reassignment of `op` inside the loop changes how gcc
compiles the hot path.  Next step: find a remap form gcc tolerates, e.g. remap through a
separate local that only the cold path reads and the hot path re-reads after the point, or
avoid the derived-view remap where the write provably cannot reach the record the view
names (the 3b index compare below), then flip the default on.

**Owner ruling relayed by the self-host session (loft-91), not yet answered:** build "3c then
3b, not runtime view tracking".  3c = a whole-value bind from a local that is dead after the
bind is a MOVE (`prog = callee_prog`, `callee_prog` dead after).  3b = at each write the view
lives across, emit `if <written index> == <viewed index> { materialise }`.  Declined: 3a, a
run-time registry of views.  What is built is static + one flag test per write site, a copy
when such a write runs while the local still views its source — not 3a, close to 3b but with
a flag instead of an index compare.  Note on 3c: in the C, `callee_prog` is itself a VIEW of
`progs[callee]` (not a materialised copy), so a move would leave `prog` a view — it needs 3b's
guard to stay sound.  Settle the form with the owner before going further.

Guard (suite, pushed as `ca2aeee`):
`loft-suite/rules/binding/B-Copy/a-deferred-copy-keeps-the-value-it-was-bound-to-whatever-the-source-does.loft`
— five cells; four fail with the copy point removed, the overwrite cell with the remap
removed (falsified under `LOFT_DEFERRED_COPY` semantics, i.e. with the rule on).
