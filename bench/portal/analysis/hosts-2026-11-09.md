# The laptop's C ship pass after @PLN219, and why the Mac read the seven higher

A record (2026-11-09).  The question: the Mac's @PLN219 session (branch `tuxedo-quality`,
handoffs in `doc/claude/plans/219-rust-slot-links/`) listed seven routines over 2.7× on the C
ship lane, while this laptop's last full table had them well under it.  Were they a set the
laptop did not measure, or the same routines reading higher?  And what does the laptop read
now that the weekend's optimisations are on `main`?

## Answer

Six of the seven are the same routines, measured here on the ship lane under both compilers;
they read 0.3–1.4× higher on the Mac.  The seventh, `lru_mixed`, was never measured here: its
bench (`bench/23_lru`) reached `main` in the #2437 join (2026-11-06), after the laptop's last
full table, which covered the library benches only.

| routine | bench | laptop 2026-11-03 gcc 15 / clang | Mac 2026-11-07 gcc-16 / clang | Mac 2026-11-08, after its fixes |
|---|---|--:|--:|--:|
| lru_mixed | core 23 | not measured | 3.45 / 3.18 | 2.63 / 2.52 |
| canvas | graphics | 2.34 / 2.34 | 3.06 / 3.19 | 2.20 / 2.23 |
| get_cell | hex_world | 1.50 / 1.89 | 2.86 / 3.03 | 2.03 / 1.73 |
| approach | fixstep | 2.17 / 2.10 | 2.88 / 2.84 | 0.98 / 0.92 |
| doc_read | hex_field | 2.25 / 2.33 | 2.75 / 3.03 | 2.22 / 2.27 |
| draw_bezier | graphics | 2.01 / 2.30 | 2.30 / 2.99 | 1.80 / 2.09 |
| materialise | zttext | 1.74 / 2.28 | 2.02 / 2.87 | 2.03 / 2.60 |

The two columns differ in more than the machine — four days of commits, gcc 15 against gcc-16 —
so the gap is read per row, not as one factor.  What it shows:

- **The platform.**  Every row reads higher on the Mac, clang the most.  Apple Silicon, Apple's
  clang, macOS's maths library and its allocator each treat the emitted C differently from the
  Rust twin.  `approach` is the clearest case: loft spelled `exp(x)` as `pow(E, x)`, and macOS's
  `pow` is far dearer than its `exp`, where glibc's is not.  `(R-ExpPow)` removed it.
- **A stale library checkout.**  The Mac's graphics checkout sat on the old `laptop-perf-bench`
  branch, so its first `canvas` number measured an old library (its handoff, § Lessons).  The
  laptop's graphics, core and plugins checkouts were on the same stale branch; they were moved to
  `main` before today's run.  The rule now stands in PERFORMANCE.md § What is judged.
- **A routine under the bar on one host is not under it on another.**  The Mac's fixes are worth
  measuring here even where the laptop already read under 2.7×.

## The fixes the weekend's optimisations needed

The optimisations reached `main` in the #2438 join.  The loft-in-loft elaborator (@PLN91), which
rebuilds recursive structures in place, then found wrong answers in them; the fixes are on
`tuxedo-pr2438-post` (not on `main` at the time of this record):

- `(R-InPlaceLiteral)`, `(R-Demote)`, `(R-Rebind)` — a literal rebuilt in place could change a
  caller's value through a by-value parameter, or lose a tree node's name (57a3e958f, 9d0238677,
  1c82c00d5, 9df2f7aea); silent, both backends.
- `(R-SameRead)`'s filed clause — the clause behind `lru_mixed`'s gain answered the deleted
  staging record of an inline table's insert, so a key of 0 lost its write on the C (d2252126a;
  `loft_hash.h`, `src/c/body/keyed.rs`).
- `(B-Scope)`, `(D-Rec)`, `(F-Block)` correctness fixes, and `(R-HostStore)`'s compile-time
  prefilter.

The benches all hashed right on `main`: the population holds few tree-rebuilding routines (the
rule beside the checkout rule in PERFORMANCE.md).  The fixes decline some rewrites in more cases,
so their cost shows as a speed difference, if any.

## The run

i7-13700H), power profile `performance`, gcc 15.3 (`cc`), `python3 bench/stats.py --lanes
rust,c,cship --no-local` over every core bench and every package `portal.library_packages()`
names, bench checkouts current with `libs.tsv`.  Merged into `bench/portal/results/laptop.tsv`
(`portal.merge_run`), so `make perf-trend` reads it against later runs.  The fix branch

move.  The laptop's earlier full tables (2026-10-29 under the `balanced` profile, 2026-11-03 v7,
library benches only) were not committed; their rows for the seven are in the table above.

## The slow routines, read in the C

Each routine over 2.7×, and each loss above, read in its ship-lane C and profiled with
`perf`.  Each suspect was checked by a pinned A/B of the program built two ways
(`taskset -c 2`, alternating runs).

- **`fill_polygon` (2.98×): the span fill of #2438.**  `loft_fill8` (`src/c/loft_cc.h`,
  `@FR-R-Fill`) writes elements one at a time up to the next 64-byte boundary, then runs a 4×
  unrolled loop, tuned on whole-canvas clears.  A polygon writes short spans and pays for both.
  The emitted program is the same as on 2026-11-06 except for the `@FR-R-Range` spellings.
  Main's runtime with the 11-06 program is as slow as main, and putting back each `R-Range`
  spelling changes nothing.  With `loft_fill8` as a plain typed loop:

  | µs per op | main | plain loop | head/unroll from 64 elements |
  |---|--:|--:|--:|
  | fill_polygon, gcc 15 | 706 | 525 (−26 %) | 609 |
  | fill_polygon, clang | 794 | 574 (−28 %) | — |
  | fill_triangle, gcc / clang | 7,510 / 15,310 | 6,260 / 11,440 | 6,380 / — |
  | canvas (a whole-canvas fill), gcc / clang | 511 / 520 | 525 / 550 | 510 / — |

  `clear`, `fill_rect` and the line routines stay within 2 %.  The plain loop gives
  `fill_polygon` its 11-06 time back (528 µs, 2.24× its twin).  `fill_circle` (drawing) gains
  3–6 % from it, which is all it lost since 11-06.  Its step against the 11-03 table came
  before 11-06 and is not located.

  **Built** (the owner's choice): `loft_fill8/4/2` are the plain typed loop.  Built and
  timed pinned against main, every output hash the same:

  | µs per op | gcc: main → plain | clang: main → plain |
  |---|--:|--:|
  | fill_polygon | 706 → 517 (−27 %) | 791 → 572 (−28 %) |
  | fill_triangle | 7,530 → 6,470 (−14 %) | 15,330 → 11,300 (−26 %) |
  | blend_pixel | 1,075 → 919 (−15 %) | 823 → 797 |
  | fill_rect | 2,889 → 2,984 (+3 %) | 4,424 → 2,939 (−34 %) |
  | canvas (a whole-canvas fill) | 520 → 557 (+7 %) | 502 → 535 (+6 %) |

  `clear`, the lines and the bezier stay within 1 %.  The head was added for a 1.4× clang cost
  on an 8-mod-16 start, measured on the Mac (@PLN219 handoff 2026-11-08); the Mac's next pass
  re-measures the canvas fills there.
- **`lru_mixed` (3.65×): the hash and the links, in the runtime.**  Self time, by cause:
  - the hash's backward-shift remove (`loft_h_remove_at`, 10–21 %).  Where the table is not
    addressed by tag, it recomputes each moved entry's key digest (`loft_ref_digest`, 3 %);
  - the table regrowing within each op (`loft_h_grow_if_full` + `loft_h_rehash_into`, 11 %);
  - the referenced bit every link write sets for `@FR-H-Removed` (`loft_bits_insert`, out of
    line, 8–10 %); every link read also tests the removed bit;
  - record claims and frees on the store's free tree (~10 %).

  The twin holds `usize` indices in a `Vec` with a free list, and pays none of these.  The
  emitted code also fills a new node's 40 bytes and then writes all four of its fields.
- **`build_index` (2.44–2.72×): the keyed insert.**  The routine is bimodal, 4.8 or 5.4 ms per
  op.  Its C is one `loft_hash_reserve`, then one `loft_keyed_entry_ints` per element; the gap
  is the generic keyed insert against Rust's `HashMap::insert`.
- **`string_build` (1.05×): no compiler change.**  Its C, and the formatter it spends 60–77 %
  in (`loft_push_decimal`), are older than the 11-03 table.  Main's build and this branch's
  give the same time pinned (ratio 1.002); separate `stats.py` passes read it at 3.43 to
  3.70 ms.

## The programs over 2.7×, written by hand

After the span fill, two routines read over 2.7× in the stored run: `lru_mixed` (3.62×) and
`build_index` (2.72×, bimodal 2.4–2.7×).  Each was written by hand in C, then the hand form and
the emitted C were priced against each other one mechanism at a time.  All runs were pinned
(`taskset -c 2`), gcc 15 `-O3`, and every output hash is the twin's.

### lru_mixed: 1.43× by hand; the gap is the runtime's layering

`bench/portal/analysis/hand/lru_mixed.c` keeps loft's semantics and data layout:
- nodes as 48-byte store records with 12-byte stored references;
- the referenced and removed bits, and a one-word tombstone for a removed referenced node
  (`@FR-H-Removed`);
- freed records parked by exact size;
- the table as the runtime builds it: power-of-two, tagged slots, linear probe, grown ×2 at half
  full, backward-shift removal by tag, and the runtime's own seeded SipHash-1-3 with its memo.

It leaves out only the runtime's generic layers.  Two switches add back the runtime's
representation costs:

| µs per op (twin 157) | time | × twin |
|---|--:|--:|
| hand | 224 | 1.43 |
| + each reference resolved through the store table (`HAND_STORETAB`) | 239 | 1.52 |
| + the table reached through its record and its header decoded per operation (`HAND_HDR`) | 291 | 1.85 |
| + both | 301 | 1.91 |
| emitted (main's runtime) | 537 | 3.42 |

The emitted program executes 10.3M instructions per op where the hand form executes 3.0M; cache
misses are negligible in both.  Priced in the emitted C, one change each, all hashes the same:

| change to the emitted C or its runtime | µs | Δ |
|---|--:|--:|
| none | 537 | |
| `@FR-H-Removed` bookkeeping removed (tombstones, the referenced bit, the removed test) — a semantics change, priced only | 447 | −17 % |
| … of which tombstones alone (`-DLOFT_NO_TOMBSTONE`) | 491 | −8.5 % |
| each link field read once, plain setters on proven non-null receivers, no prefill of a fully written node (on the 447 row) | 443 | −1 % |
| `loft_st_note_referenced` tests the bit before the call | 525 | −2 % |
| + `loft_bits_insert` inline, its growth path cold | 520 | −3 % |
| + a typed lookup and insert specialised to the tagged, record-entry table (the lookup alone: 522) | 506 | −6 % |
| + `loft_ilog2` by count-leading-zeros (it loops; every header decode calls it) | 497 | −7 % |
| + `loft_digest_i64` reads each SipHash word at once (`loft_sip_le` loops over bytes) | 485 | −10 % |

None of these is one large missing rewrite.  The gap is the runtime re-deriving facts that hold
for the whole operation, and doing generic work where the case is known:
1. **The table header per operation** (the largest structural cost, +67 µs in the hand form).
   Every hash call goes record → collection slot → table claim → word count, flags, seed and
   entry kind before it probes.  A table handle resolved once and passed to typed operations, as
   the vector handle `loft_vh` already does for vectors, removes it; an insert that can grow the
   table re-resolves it, as a push does for a vector handle.
2. **`@FR-H-Removed` as bits and tombstones** (−17 % if absent).  Every link write sets a
   referenced bit that is never cleared, so each evicted node becomes a tombstone even when no
   link names it any more.  Making it cheap needs a design decision (for example generation-
   checked references, which also let a freed record be reused at once); it is an owner call.
3. **Store bookkeeping out of line** (the bits, the delete and claim paths): the inline fast
   paths above, −3 %.
4. **Runtime helpers that loop** (`loft_ilog2`, `loft_sip_le`): −4 % together, and they sit under
   every hash operation in every program.
5. **The emitted code itself is not the gap** (−1 % from read-once fields and plain setters).

### build_index: 1.30× when it runs alone

`build_index` alone in its bench program runs 2.45–2.53 ms per op against the twin's 1.94
(1.30×).  After `collect_dirty_inputs` in the same process it runs 3.25–3.50 ms, and in the full
bench program 4.45 ms (2.3×).  Inside the routine the call counts are identical in every build
(100,000 keyed inserts, one rebuild, one reserve per op), and so are the probe steps (1.31 per
insert).  Inlining the keyed insert or not moves it 10 %; forcing it inline in the full program
makes it slower.  The routine's reading over 2.7× is therefore the C compiler's inlining and
layout across the whole bench program, plus the heap state the routine before it leaves.  It is
noted here, not fixed (the owner's rule on layout).  The two runtime helpers above (`loft_ilog2`,
`loft_sip_le`) take 4 % off it in the full program.
