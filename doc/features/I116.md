# @I116 — Library placement — in-process, a worker, or another machine

## What it does

Decides **where** a library's functions run — in this process, in a worker process on this machine, or on a server elsewhere — from one line of the library's own manifest, with the consumer's source unchanged:

```toml
[library]
placement = "inproc" | "process" | "remote"
```

The invariant it holds is that you cannot tell from the program: a call to a library is indistinguishable, in type, effect, ownership/lifetime and error behaviour, from the same call in-process. Where it runs is deployment policy, not source.

A struct or a vector crosses as **itself** — a shared memory-mapped loft store for a worker on this machine, the same store's bytes on a socket for a remote one — rather than being encoded into a second wire vocabulary. That is possible because nothing inside a store is a pointer: a record graph's interior references are plain `u32` record ids, so it is independent of both the address it is mapped at and the store number it is registered under.

What it buys: fault isolation (a crash inside the library ends the call as a loft error instead of taking the program's data with it), and the ability to put a library on the machine that should hold it.

Not everything can be placed, and the rules are the library author's to follow — a public function must not itself be a native, the surface should answer a value rather than a cursor, closures do not cross, and a function returning a borrowed VIEW of something it did not create is refused rather than mis-marshalled. A signature outside what the boundary carries simply runs in-process, byte-identically; nothing becomes a call that fails later.

## Where it lives

`src/lib_placement.rs` (declaration), `src/lib_placement/arena.rs` (the shared store a compound value crosses in), `src/lib_placement/wire.rs` (both transports and both ends), `src/lib_placement/dispatch.rs` (routing a placed library's calls).
