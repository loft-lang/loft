# @F4 — Ranged/width integer types (u8/i8/u16/i16/i32/u32)

## What it is

Besides the everyday `integer`, loft offers smaller number types sized to their range: `u8`, `i8`, `u16`, `i16`, `i32`, `u32`. Each holds whole numbers within fixed bounds and takes up less space.

## How it aids you

When you store many numbers you know stay small — a colour channel (0..255), an age, a year — these compact types keep your data small and your intent clear, while you still write and read them like ordinary numbers.

## Example

```loft
fn main() {
    level: u8 = 200;      // fits in a single byte (0..255)
    year: u16 = 2026;     // fits in two bytes
    temp: i8 = -40;       // small signed value
    println("{level} {year} {temp}");   // 200 2026 -40
}
```


## Where the bounds are enforced — one answer, in every position

Every position now bounds the value the same way, and a result that does not fit takes the
type's **default** — never a wrapped or truncated one, which would be in range,
type-correct and unrelated to the calculation (`formal/operational.md` `(E-Uncomp-NN)`).

| position | out-of-range | result |
|---|---|---|
| declaration — `l: u8 = 300` | | refused: *"cannot implicitly narrow integer to u8"* |
| written-out assignment — `l = l + 10` | | refused, same message |
| compound assignment — `l: u8 = 250; l += 10` | 260 | `0` |
| `b: u8 = 5; b -= 10` | -5 | `0` |
| struct field — `u.a += 253` from 7 | 260 | `0` |
| vector element — `v[0] += 253` from 7 | 260 | `0` |

`i32` is the one exception, and it is a representation fact rather than a rule change: it
keeps `i32::MIN` back for null, so its overflow reads as `null` where the other five, which
use every code they have, read as the default.

## Choosing the value, and seeing that it did not fit

Because the five that fill their range have no code left for a failure, `0` from an overflow
and a computed `0` are the same value. Two spellings — both ordinary, neither new — let an
author who cares about that edge handle it:

```loft
n: integer = 400;
level: u8 = n ?? 255;        // 255 — YOUR value instead of the type's default

health: u8 = 250;
health += 10;
if !health { … }             // true: the store did not fit (health is 0, as it would be anyway)
```

The `if` has to be the **very next** statement after the store — further away there would be
nowhere to keep the answer but the number itself, which would cost a `vector<u8>` the byte
the type was chosen for. Move it and the compiler tells you the check stopped working rather
than letting it go quiet.

The storage half of the promise holds exactly: `u8` is 1 byte, `u16` 2, `i32`/`u32` 4,
against `integer`'s 8, and a struct is their packed sum — `{ a: u8, b: u16, c: i8 }` is 4. A
`vector<u8>` of three elements is three bytes.
