# @F4 — Ranged/width integer types (u8/i8/u16/i16/i32/u32)

## What it is

Besides the everyday `integer`, loft offers smaller number types sized to their range: `u8`, `i8`, `u16`, `i16`, `i32`, `u32`. Each holds whole numbers within fixed bounds and takes up less space.

## How it aids you

When you store many numbers you know stay small — a colour channel (0..255), an age, a year — these compact types keep your data small and your intent clear, while you still write and read them like ordinary numbers.

## Example

```loft
fn main() {
    level: u8 = 200;      // fits in a single byte (0..255)
    year: u16 = 2026;     // fits in two bytes
    temp: i8 = -40;       // small signed value
    println("{level} {year} {temp}");   // 200 2026 -40
}
```


## Where the bounds are enforced — one answer, in every position

Every position now bounds the value the same way, and a result that does not fit takes the
type's **default** — never a wrapped or truncated one, which would be in range,
type-correct and unrelated to the calculation (`formal/operational.md` `(E-Uncomp-NN)`).

| position | out-of-range | result |
|---|---|---|
| declaration — `l: u8 = 300` | | refused: *"cannot implicitly narrow integer to u8"* |
| written-out assignment — `l = l + 10` | | refused, same message |
| compound assignment — `l: u8 = 250; l += 10` | 260 | `0` |
| `b: u8 = 5; b -= 10` | -5 | `0` |
| struct field — `u.a += 253` from 7 | 260 | `0` |
| vector element — `v[0] += 253` from 7 | 260 | `0` |

The plain `integer` and `i32` are the exceptions: an overflow in either reads as `null`,
not as the default. The other four, plus `u32` and every `limit(lo, hi)` type you declare
yourself, read as the default.

`i32` is the one worth understanding, because it is a deliberate trade rather than a
different kind of type. It gives up exactly one value — `-2147483648`, which is why
`x: i32 = -2147483648` does not compile — to keep a code that means *absent*. One number in
four billion, and in exchange it is the only compact integer type whose overflow your
program can notice on its own. `u32` gives up a value too (`4294967295` does not compile
either), and there that code is **not** a null: a `u32` overflow reads `0` like the rest.
So reach for `i32` when you want an overflow to be visible, and do not assume the same of
`u32` because the two look symmetric.

### Your own ranged types answer the same way

`type Health = integer limit(0, 100) size(1)` is 101 values in a byte's 256, so 155 codes
sit unused inside it. Those spare codes are **not** a place to keep a null: a value that
does not fit takes `Health`'s default, exactly as `u8` does. Whether a range happens to
leave room is arithmetic you did not do — `limit(-100, 100) size(1)` and
`limit(-128, 127) size(1)` are one value apart — so it cannot decide what your program
answers.

The default is the value the program would have had if nobody had assigned: zero where the
range holds it, otherwise the bound nearest zero. `integer limit(1000, 1100)` defaults to
`1000`, not to `0`, because `0` is not one of its values.

## Choosing the value, and seeing that it did not fit

Because the five that fill their range have no code left for a failure, `0` from an overflow
and a computed `0` are the same value. Two spellings — both ordinary, neither new — let an
author who cares about that edge handle it:

```loft
n: integer = 400;
level: u8 = n ?? 255;        // 255 — YOUR value instead of the type's default

health: u8 = 250;
health += 10;
if !health { … }             // true: the store did not fit (health is 0, as it would be anyway)
```

The `if` has to be the **very next** statement after the store — further away there would be
nowhere to keep the answer but the number itself, which would cost a `vector<u8>` the byte
the type was chosen for. Move it and the compiler tells you the check stopped working rather
than letting it go quiet.

And the compound step now says so itself, so you find out without going looking:

```
advice[narrow-fallback]: a step past `0..255` takes this type's default, `0` —
                         nothing here says which values the step may produce
```

It is advice rather than a warning: the default is what the language promises for a value
that does not fit, so ignoring it cannot give you a result the language did not describe.
It goes quiet as soon as you write either cure above — the `if !health` next door, or a
`health = (health + 10) ?? 255` that names your own fallback — and it never appears for a
type that keeps a code for its own failure, where `!` reads the failure anywhere.

The storage half of the promise holds exactly: `u8` is 1 byte, `u16` 2, `i32`/`u32` 4,
against `integer`'s 8, and a struct is their packed sum — `{ a: u8, b: u16, c: i8 }` is 4. A
`vector<u8>` of three elements is three bytes.
