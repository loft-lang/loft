# @F1 — Nullable value semantics — in-band sentinels + null-fallback arithmetic

## What it is

A value can be present or absent. An absent value is `null`. Doing arithmetic with a `null` simply produces `null` again instead of stopping your program.

Null costs no space, because each type spends one of its own values on it — an **in-band sentinel**:

| type | the value that means null |
|---|---|
| `integer` | the most negative 64-bit integer |
| `float` / `single` | NaN |
| `boolean` | `false` |
| `character` | the NUL character (code point 0) |
| `text` | a single NUL character — the empty string `""` is NOT null |
| a reference | record 0 |
| a plain `enum` | byte 255 (which is why an enum stops at 255 variants) |

So a value that happens to BE the sentinel reads as absent. `false` is the one to know: for a boolean, "not set" and "set to false" are the same value, and no check can separate them.

## How it aids you

Missing data — a lookup that found nothing, a field never filled in — no longer has to be a special case that crashes. The absence flows through your calculation as `null`, so you can carry on and decide what to do about it at the end rather than guarding every step. Nothing is boxed and nothing is wrapped, so an optional value costs exactly what the value costs.

The price is that null is a value of the type, not a separate thing beside it. For a `boolean` that bites at once, since its null IS `false`; for an `integer` the reserved value is one real arithmetic almost never reaches. The same shape then repeats one level up, in any API that answers a legitimate value to mean "nothing here" — and there the collision is ordinary rather than rare, so the bound has to come from somewhere else.

## Example

```loft
fn main() {
    a = null as integer?;  // a holds no value
    b = a + 10;            // arithmetic on null gives null, no crash
    println("{a} {b}");    // null null
    println("still running");
}
```
