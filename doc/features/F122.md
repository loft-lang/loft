# @F122 — Multiple dispatch — one name, a definition per combination of parameter types

## What it is

A function name may have several definitions, told apart by the types of ALL their
parameters. Loft picks the most specific definition that fits the arguments: a variant beats
its enum, so `hit(f: Fireball, w: IceWall)` wins over `hit(a: Entity, b: Entity)` for that
pair, and the enum-level definition answers every pair nothing more specific takes. When a
value is held as the enum, the choice is made from the variant it holds at run time.

## How it aids you

Behaviour that depends on two kinds of thing at once — fire against an ice wall, fire against a
crate — is written as one small definition per case instead of one big `match` on a pair that
grows with every new kind. The enum-level definition is the fallback, like `_` in a `match`.
Two definitions that fit equally well, or a call through the enum that no definition covers,
are refused when the program is compiled, never discovered at run time.

## Example

```loft
enum Entity {
    Fireball { power: integer },
    IceWall { thickness: integer },
    Crate { weight: integer }
}
fn hit(f: Fireball, w: IceWall) -> text {
    "fire melts the wall"
}
fn hit(f: Fireball, c: Crate) -> text {
    "fire burns the crate"
}
fn hit(a: Entity, b: Entity) -> text {
    "they bump"
}
fn main() {
    things: vector<Entity> = [Fireball { power: 3 }, IceWall { thickness: 2 }, Crate { weight: 5 }];
    for a in things {
        for b in things if a#index != b#index {
            println(hit(a, b));   // fire melts the wall, fire burns the crate, then four bumps
        }
    }
}
```
