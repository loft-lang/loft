# @F92 — Direct C binding — `#c "symbol" "signature"`, no rustc and no glue crate

## What it is

Declare a C function in loft and call it. You write the symbol name and its C signature on the declaration — `fn c_abs(v: integer) -> integer;   #c "abs" "int(int)"` — and that is the whole binding: no wrapper crate, no build script, no code generator, and no Rust toolchain.

The signature string is what loft uses to marshal the call, so the declaration is the only place the C types are written down. A `[c] libs` entry in `loft.toml` names a library to load; `[c] optional-libs` marks one that may be absent, and `c_library_available("libfoo.so.1")` asks before calling. A `[c] shim` entry names ANSI-C sources loft compiles for you with `cc`, for the shapes a direct call cannot express — the list is in the third boundary below.

## How it aids you

Use the C library that already exists instead of waiting for someone to port it. Because the declaration carries the signature, there is nothing to keep in sync — no second file that can drift from the first — and because C already has a stable ABI and a name-addressable symbol table, loft needs no generated adapter the way a Rust binding does. Installing a `#c` library needs a C library on the machine and nothing else.

A loft `text` arrives as `const char*` — a pointer to its UTF-8 **bytes**. So a C function that counts them agrees with `size()`, never with `len()`, which counts characters; the two answers come apart the moment the text stops being ASCII.

**Three boundaries to know.**

**The register class**, which is the one you meet first. Every argument and the return travel through fixed integer-class trampolines, so what a binding can express is decided by the register class of each slot — not by its width, and not by how exotic the function is. Integers and pointers (and therefore a `text`) cross directly. A 64-bit **float argument** does not: it travels in an SSE register the caller never writes, so `#c "fabs" "double(double)"` is refused. The two ends of one signature part company here — a float **return** crosses fine, which is why `#c "atof" "double(const char*)"` binds and `double(double)` does not. Also refused: a nullable value (C has no null model), a struct by value, varargs, an out-parameter, and a `vector` whose element width does not match the C pointee. Each has an ANSI-C shim as its cure, which is what `[c] shim` is for. A binding covers **0..=32** C arguments; the 33rd is `error[c-binding-not-interpretable]`. Unlike the wasm boundary below, this refusal is not call-site-conditional — the declaration alone fails the build, with the function never called.

**wasm.** A wasm module cannot open a shared library, so `--native-wasm` and `--html` refuse a `#c` call in one message naming the function, the symbol, the package and the target — here a declaration *is* still portable and only a *call* is refused, so a library may carry `#c` bindings and still build for wasm as long as the wasm program does not reach one.

**The sandbox.** Under `--sandbox` a `#c` binding is gated by `native_ffi`, never by a `#cap` grant: a capability says what data a script may touch, and a C call runs machine code loft cannot inspect.

## Example

```loft
fn c_abs(v: integer) -> integer;      #c "abs" "int(int)"
fn c_strlen(s: text) -> integer;      #c "strlen" "size_t(const char*)"
fn c_atof(s: text) -> float;          #c "atof" "double(const char*)"

fn main() {
    println("abs: {c_abs(-7)}");           // abs: 7
    println("strlen: {c_strlen("loft")}"); // strlen: 4
    // A float RETURN crosses; a float ARGUMENT would need an ANSI-C shim.
    println("atof: {c_atof("2.5")}");      // atof: 2.5
}
```
