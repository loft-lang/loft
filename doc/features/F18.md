# @F18 — `const` parameters

## What it is

Put `const` in front of a parameter's type to say this function does not change that value. Every write THROUGH the parameter is a compile error — `p.f = …`, `p[i] = …`, `p += …`, and nested writes under them — so the read-only accessor style is checked rather than promised in a comment.

The promise travels with the value. A view of it — a loop variable over its elements, an element or field bound to a local — is read-only too, and handing it ON is checked at the call: a `&` parameter refuses it, and a plain record or collection parameter reports it (the warning `const-to-plain-parameter`, an error once the shipped libraries have migrated) unless that parameter is itself `const`. A plain struct parameter names the caller's value (@F106), so the parameter's declaration is what says whether the callee may write — not whether its body happens to. The standard library's readers (`len`, `sum`, `join`, the JSON accessors) declare `const`. The one gap left is a function reference: `fn(const T)` is not spelled yet, so a value passed through one is not checked.

## How it aids you

Anyone reading the signature knows this function will not write your data, and if its body ever tries, the compiler says so straight away instead of leaving you to chase a surprise. That is what makes an accessor-style API — `length3(v: const Vec3)`, `mesh_to_floats(m: const Mesh)` — worth reading: the promise is in the type, checked, and costs no copy.

Where the value travels further, it stays read-only: pass it to a `const` parameter, or copy what you change into a local.

## Example

```loft
struct Account {
    balance: integer
}
fn describe(acct: const Account) -> text {
    "balance is {acct.balance}"
}
fn main() {
    a = Account { balance: 500 };
    println(describe(a));           // balance is 500
    println("still {a.balance}");   // still 500
}
```
