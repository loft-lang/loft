# @F100 — Dead-code lint — a local never read, and a write whose value is lost

## What it is

A lint that points out a local you never read, and a write whose value nothing ever uses — including the case where you copied a collection, changed the copy, and the change went nowhere.

## How it aids you

The dangerous half is the silent one. `d = self.data; d[i] = x` binds a **copy**, so the write is lost and the program keeps running with the original data. A published drawing library shipped every one of its primitives as a no-op through exactly that shape. The lint names the line instead of leaving you to notice the missing output — and it names the function that made the copy, not the call site, which is where a reader would otherwise start looking.

## Example

```loft
struct Canvas { data: vector<integer> }

// `d = self.data` binds a COPY of the vector, so the write lands in the copy and is lost:
// loft warns `lost-write` on this line, naming `d`.
fn paint_lost(self: Canvas, i: integer, colour: integer) {
    d = self.data;
    d[i] = colour;
}

// Writing through the record's own field changes the canvas.
fn paint(self: Canvas, i: integer, colour: integer) {
    self.data[i] = colour;
}

fn main() {
    c = Canvas { data: [0, 0, 0] };
    c.paint_lost(1, 7);
    println("{c.data}");   // [0,0,0] — the write went into the copy
    c.paint(1, 7);
    println("{c.data}");   // [0,7,0]
}
```

The first call's write is lost, and loft says so where it happens:

```
warning[lost-write]: 'd' is mutated but its value is never read — the write is LOST. A whole-value bind (`d = …`) COPIES the heap value, so the mutation lands in the copy, not the source.
  --> canvas.loft:6:8
  |
6 |     d = self.data;
  |        ^
```

Both halves are **warnings**, not advice — ignoring one produces a wrong answer, which is loft's rule for the gating tier — so a build run with `LOFT_DENY_WARNINGS=1` stops on them. `LOFT_NO_DEAD_STORES=1` turns the lost-write half off.

It runs under `loft test` as well as on the program path, so a library's own CI sees it. One limit worth knowing: guarding with `if i < len(d)` does **not** count as reading `d` — a length cannot witness an element write.
