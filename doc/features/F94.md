# @F94 — Type-directed interpolation — a type receives the literal/hole boundary

## What it is

A format string does not have to become one flat text. Give the target type `lit` and `hole_*` methods and it receives the pieces separately: the literal chunks **you** typed reach `lit`, and each interpolated value reaches `hole_text` / `hole_int` / `hole_float` / `hole_boolean` / `hole_character` as a value, not as rendered text.

Writing `q: Query = "SELECT id FROM people WHERE name = {name}"` lowers to `q.lit("SELECT id FROM people WHERE name = "); q.hole_text(name);` — so the type decides what a hole becomes. A kind the target does not accept is a compile error naming the method to add, never a silent fall back to text.

## How it aids you

Injection stops being a rule you can forget. Because the only path into the statement text is `lit`, and `lit` only ever receives bytes from your source file, a value has no route into SQL syntax — by construction rather than by discipline. The same shape builds shell commands, HTML, paths and structured log records safely, and you write an ordinary format string to do it.

## Example

```loft
struct Query { text: text, values: vector<text> }

pub fn lit(self: Query, s: text) { self.text += s; }
pub fn hole_text(self: Query, v: text) {
    self.text += "?";
    self.values += [v];
}
pub fn hole_int(self: Query, v: integer) {
    self.text += "?";
    self.values += ["{v}"];
}

fn main() {
    name = "ada; DROP TABLE users; --";
    q: Query = "SELECT id FROM people WHERE name = {name} AND age > {30}";
    println("sql:    {q.text}");
    println("values: {q.values[0]}");
    println("count:  {len(q.values)}");
}
```


## A hole can also be a named type

A hole is not limited to the scalar kinds. A value of a struct or enum type reaches a method named after that type, spelled the way loft methods are spelled — so `SqlIdent` asks for `hole_sql_ident` and `Level` for `hole_level`. An acronym run breaks at the last capital, so `SQLIdent` is also `hole_sql_ident`.

```loft
fn hole_sql_ident(self: SqlText, v: SqlIdent?)
fn hole_level(self: Trace, v: Level)
```

The name is DERIVED, never chosen, so a target and the compiler cannot disagree about what a type's hole is called — and the error for a missing one can name the exact method to add.

This is what lets a target hold something apart from both a literal and a bound value. A SQL table name really is syntax, not data, so it cannot travel as a bound parameter — but letting it through as a literal would reopen the hole this feature exists to close. As its own type it goes inline, and the safety rests on the TYPE: nothing builds a `SqlIdent` except its validating constructor, so there is one method and one constructor to audit.

## Two refusals, on purpose

- **A kind the target does not define is a compile error**, naming the method to add. It never falls back to text, because that would put a value back on the path this exists to close.
- **A spec on a hole is refused** — `{v:>8}` has already decided how the value should LOOK, and the target wants the value. If a target ever needs formatting, the hole reaches it as data and the target renders it.
