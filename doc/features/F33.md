# @F33 — `par(...)` parallel for-loop

## What it is

Adding a `par(...)` clause to a `for` loop runs its work across several threads at once. Each item is handed to a worker function, and the loop body then sees that worker's result — **in source order**, not in the order the workers finished. So the body can append results to a vector and get them back in the order it iterated, not just fold them into a sum.

A worker runs on an isolated store clone, so what it may CAPTURE is restricted and the compiler enforces it: captured arguments must be scalars (`integer`, `float`, `boolean`). A captured `text`, struct or collection is refused — `text` counts as a reference — and a worker that WRITES captured state is refused separately as a data race. The loop ELEMENT is the exception and may be a reference, which is why `for r in rows par(b = work(r), 4)` is the shape to reach for. A worker may still RETURN a reference type; it is only the capture that is restricted.

## How it aids you

Independent, repeated work finishes faster by using more than one processor core — with no manual thread handling. You write an ordinary loop and add one clause.

On eight equal items the measured speedup was about 2.0x at 2 workers, 3.2x at 4 and 4.7x at 8. The second number in the clause is the worker count; anything from `0` upward is accepted and a count larger than the number of items is not special.

"No manual thread handling" is not a promise you have to trust — a shape that would race does not compile, so there is no runtime race to debug.

## Example

```loft
fn square(n: integer) -> integer {
    n * n
}

fn main() {
    // Each number is squared on a worker thread; b holds the result.
    total = 0;
    for a in 1..=5 par(b = square(a), 4) {
        total += b;
    }
    println("sum of squares 1..5: {total}");   // sum of squares 1..5: 55
}
```
