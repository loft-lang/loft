# @F21 — References `&T` — parameters, bindings + place returns

## What it is

Put `&` before a parameter's type to pass a variable by reference. The function then works on your actual variable, so any change it makes stays after the call returns. The call is written without `&`: `add_to(total, 5)`. A `&` parameter the function never writes is a compile error (*"has & but is never modified; remove the &"*).

A local can hold a reference too: `b = &a` makes `b` another name for `a`, so `b += 1` changes `a`.

A function's return type can carry `&` as well: `fn side(p: Pair, left: boolean) -> &Counter { if left { p.left } else { p.right } }` returns the **place** inside `p`, not a copy (`-> const &Counter` when `p` is `const`). Every place the body can return must live in **one** parameter's lifetime, and the body writes the plain place (`p.left`, never `&p.left`). At the call site, `side(pair, true).n += 5` and `reset(side(pair, true))` act on `pair.left` directly; a plain binding `c = side(pair, true)` views a record or collection and copies a scalar or text, while `c = &side(pair, true)` links in every case.

`&` on a parameter is what a **scalar** needs. Without it an `integer`, `float`, `boolean`, `character` or `text` parameter is a copy: the callee's write is gone when the call returns, and the new value has to travel home in the return instead. A **tuple** parameter is a copy as well, the records and collections inside it included: `fn f(t: (integer, P))` may write `t.0` and `t.1.n` and the caller's tuple keeps its values; `t: &(integer, P)` is the form that writes back.

A **struct, value struct or collection** parameter is not a copy — it names the caller's own record, so a field or element write through it lands with or without `&`. loft says so itself: a `&` whose only write is a field earns `advice[slow-reference-parameter]`, *"field mutation already propagates to the caller without it"*.

What `&` still buys for those parameter types is **replacing the whole binding**. `s = S { … }` inside the callee reaches the caller only through `&`; without it the new value dies with the call. Nothing at the call site says so, but the callee does: a plain parameter whose incoming value is replaced unread, or whose new value nothing reads, is a `warning[never-read]` / `warning[dead-assignment]` whose fix line is `b: &…`.

## How it aids you

Let a function update your data in place — add to a running total, adjust a counter, hand back a parsed value through an out-parameter — without you having to catch a result and assign it back. For a scalar that is the difference between a helper that can update your counter and one that cannot; for a struct or a collection it is the visible way to say the callee may replace the whole thing, not just write into it. On a return, `-> &T` lets you name an indexing or lookup path once (`side(pair, left)`, `cell(grid, x, y)`) and still write through it without copying or repeating the path at every call site.

## Example

```loft
struct Counter { n: integer }
struct Pair { left: Counter, right: Counter }

fn add_to(x: &integer, amount: integer) {
    x += amount;
}

fn side(p: Pair, left: boolean) -> &Counter {
    if left { p.left } else { p.right }
}

fn main() {
    total = 10;
    add_to(total, 5);                   // no `&` at the call
    add_to(total, 100);
    println("total = {total}");         // total = 115
    alias = &total;                     // a local reference
    alias += 1;
    println("total = {total}");         // total = 116
    pair = Pair { left: Counter { n: 1 }, right: Counter { n: 2 } };
    side(pair, true).n += 5;            // -> &Counter writes pair.left in place
    println("left = {pair.left.n}, right = {pair.right.n}"); // left = 6, right = 2
}
```


## One rule to know

A `&` is an ownership decision, so loft keeps its promise or refuses the program — it will
never quietly hand you a copy instead. Taking a reference into a container — directly or
through a `-> &T` call — and then **disturbing that container while the reference is still in
use** is a compile-time error. Four events end the place the reference names: removing from
the container, growing it (`v += [x]`, an insert), writing a key field through the reference,
and replacing the container outright. They count in a called function too.

```loft
c = &v[0];
c.n = 99;      // fine — finished with `c` before `v` changes
v.remove(2);

c = &v[0];
v.remove(2);   // error: cannot remove from `v` while `c` references a place inside it
c.n = 99;
```

Only *liveness* matters, so moving the last use of the reference above the change is the
usual fix.

A plain binding without `&` works differently. `c = v[0]` (or `c = first(v)`) on a vector of
records is a **view**: `c.n = 50` writes into `v[0]`. It becomes a copy only when `v` is
disturbed while `c` is still in use, and loft says so with an advice (*"`c` was copied out of
`v` because `v` grows while `c` is in use … Writes through `c` no longer reach `v`"*). The
program still compiles; writes through `c` just stop reaching `v` (@F106).
