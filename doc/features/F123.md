# @F123 — Foreign stores — a mapped file or a library's buffer read in place, a slice of it a view

## Example

```loft
fn main() {
  assert(write_bytes("hello.bin", [104, 101, 108, 108, 111]), "write");
  m = file_map("hello.bin") ?? [];
  assert(len(m) == 5 && m[0] == 104, "the file's bytes, read in place");
  word = m[1..4];
  assert(text_from_bytes(word) == "ell", "a slice is a view of the mapping, not a copy");
  w = m;
  w[0] = 72;
  assert(w[0] == 72 && m[0] == 104, "a bind copies, and the copy is writable");
  println("{text_from_bytes(m)}");
}
```

## What it is

A `vector<u8>` (or a `vector<single>`) can be served from bytes loft does not own — a
mapped file (`file_map(path)`), a native library's own buffer (a bridge answering
`foreign_vector_from_owned`), later a host frame — through the same store contract every
vector read uses, with no copy into a store.  Every read works as on any vector: the length,
an index, an iteration, a hoisted loop, `text_from_bytes`, an argument to a function or a
library.  A slice bound to a local (`s = m[lo..hi]`) is a VIEW of the bytes, not a copy, and a
library's whole answer bound to a local is one too.  Such bytes are read-only: a write into
them (`m[0] = 1`, `m += […]`) stops the program with the advice to copy first — `w = m`, a
bind, copies, and the copy is an ordinary vector.  The bytes live for as long as any handle
or view over them is bound, in any order of freeing.

## How it aids you

A decoder reads a file, a frame or a library's payload where it lies, and takes each field
as a slice, without first copying the whole thing into a vector and each field out of it
again.  A 4 KiB payload decoded through cbor went from 41.9 to 17.3 ms per thousand reads
for that reason.  The read-only rule is what makes it safe: nothing can grow or move the
block under a loop that has already taken its base, and a program that needs to change
the bytes says so by copying them.
