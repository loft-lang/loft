# @I117 — Git query natives — a repository as a typed library, not a subprocess

## What it does

Lets loft read a git repository through a typed library — `git::log(20) -> vector<Commit>`, `git::changed(base) -> vector<Change>`, `git::tracked_files() -> vector<text>` — instead of through a subprocess primitive. loft deliberately has no `run(cmd, args)`: it hands back bytes and an exit status, and every caller then re-parses text loft already knows how to type.

So the `execve` lives inside one vetted library, and the natives behind it are a **closed query vocabulary**: the caller names a question and loft builds the command. Nothing composes a command line, which is what removes the injection surface by construction rather than by filtering — `git -c core.sshCommand=…` is unreachable, a path always follows `--`, and a ref may not begin with `-`. Reading a repository needs the library's own `git#read` capability, separately from reading files.

Registered for both backends, so a compiled program can ask git too.

## Where it lives

`src/git_query.rs` (the vocabulary and both backends' entry points), registered in `src/native.rs` and `src/codegen_runtime.rs`; the typed loft surface is `lib/git/`.

First consumers: `tools/viewer/refresh.loft` (which replaced 135 lines of bash and the review dashboard's dependency on `jq`) and `tools/indexer/src/scan.loft` (which asks which files the repository carries instead of mirroring `.gitignore` by hand).
