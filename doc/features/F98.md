# @F98 — `spatial<T[x,y]>` — position-keyed collection for proximity queries

## What it is

`spatial<T[x, y]>` (and `spatial<T[x, y, z]>`) is a keyed collection ordered by **position**. It stores records by their coordinate fields so you can ask what is near a point instead of scanning everything.

## How it aids you

Proximity questions — which mobs are near this one, what is in view, what might collide — stop being a full scan. Ordinary subscript and slice syntax does the asking; there are no special methods to learn.

## Example

```loft
struct Mob { x: integer, y: integer, name: text }

fn main() {
    mobs: spatial<Mob[x, y]> = [];
    mobs += [Mob { x: 10, y: 10, name: "goblin" }];
    mobs += [Mob { x: 12, y: 11, name: "rat" }];
    mobs += [Mob { x: 90, y: 90, name: "dragon" }];

    println("point {mobs[10, 10].name}");        // point goblin

    seen = "";
    for m in mobs[(10, 10)..:2] { seen = seen + m.name + " " }
    println("nearest two: {seen}");              // nearest two: goblin rat
}
```

`xs[x, y]` reads, writes or removes one point. `xs[(x1,y1)..(x2,y2)]` takes a **box** and gives you exactly what is inside it — nothing outside, in the collection's own order; a corner-swapped axis names the same box. `xs[(x,y)..]` and `xs[(x,y)..:n]` walk OUTWARD from a point, nearest first, and the next section is what that means exactly. One to three axes; a fourth is refused (*"supports at most 3 coordinate axes, got 4"*).

## The open forms walk outward, and are approximate

`xs[(x,y)..]` and `xs[(x,y)..:n]` yield records in roughly-increasing distance from the query — two cursors seeded either side of it, each step taking whichever is closer. So the answer does not depend on where the query sits: a cap of `n` gives you `n` records from any point, and a query past everything on the map still gets its neighbours.

```loft
struct Mob { x: integer, y: integer, name: text }

fn main() {
    mobs: spatial<Mob[x, y]> = [];
    mobs += [Mob { x: 10, y: 10, name: "goblin" }];
    mobs += [Mob { x: 12, y: 11, name: "rat" }];
    mobs += [Mob { x: 90, y: 90, name: "dragon" }];

    // From the rat, the goblin is two steps away and the dragon a hundred.
    seen = "";
    for m in mobs[(12, 11)..:2] { seen = seen + m.name + " " }
    println("{seen}");                  // rat goblin
}
```

**Approximate, and that is the one thing to know before you rely on it.** The order is by distance along the collection's space-filling curve, which tracks real distance closely but jumps at quadrant boundaries — so a very close point can occasionally arrive a place later than a slightly further one. Every record is yielded eventually, each once, so a `break` is how you stop.

When the answer must be exact, use the **box**: `xs[(x-r, y-r)..(x+r, y+r)]` gives you precisely what is inside it, in every direction (loft#800).

Over five records at `(0,0)`, `(5,5)`, `(10,10)`, `(12,11)`, `(20,20)`, a cap of **3**:

| query | answered |
|---|---|
| `(0,0)..:3` | A B C |
| `(5,5)..:3` | B A C |
| `(10,10)..:3` | C D B |
| `(12,11)..:3` | D C B |
| `(20,20)..:3` | E D C |
| `(99,99)..:3` | E D C |

Three from every origin, including one past every record. These forms used to be the Morton **tail** — records at or after the query only — so a record one code behind never appeared however close it was, `..:n` silently answered 3, 3, 3, 2, 1, 0 down that column, and an entity at the far edge of the map asking for the three things nearest it got nothing at all (loft#1002).
