# @F107 — Type reflection — the declared shape of a type, as data

## What it is

`type_of(x)` hands a program the declared shape of a type as ordinary data — its name, the bytes one record occupies, and every field with its own name, type name and byte offset. An enum reports its variants; a vector or keyed collection names its element type. When the name only arrives at runtime — from a config file, a database catalogue, a command line — `type_named("Row")` asks the same question with no value in hand, and answers `null` when this program has no such type.

`field_value(x, position)` is the other half: what a VALUE holds at one of those positions. `type_of` says a record has a `text` at byte 16; this reads it. A field of an **inline struct** is reached with a PATH instead — `field_value(doc, [8, 0])` is `doc.origin.x` — because a nested record reports its fields relative to itself, so one number cannot name a field inside one.

## How it aids you

A generic serialiser, an ORM mapping or a schema check can be written once, against any type, instead of once per type by hand. The answer is read from the same layout descriptor the store and the browser bridge already use, so reflection cannot drift into a second, disagreeing description of the same memory — and because both halves read that one descriptor, a position `type_of` hands out is a position `field_value` can read.

## Example

```loft
struct Point { x: integer, y: integer }
struct Row { id: integer, origin: Point, name: text? }

fn main() {
    row = Row { id: 7, origin: Point { x: 3, y: 4 }, name: null };

    t = type_of(row);                       // the TYPE of row, not its value
    println("{t.name} — {t.size} bytes");
    for f in t.fields {
        // ... and what THIS row holds there. `null` is not `""`.
        v = field_value(row, f.position);
        shown = if v.is_null { "null" } else if v.kind == TextKind { v.t }
                else if v.kind == IntegerKind { "{v.i}" } else { "(descend)" };
        println("  {f.name}: {f.type_name} @{f.position} = {shown}");
    }

    // An inline struct holds no value of its own — reach INTO it with a PATH.
    // [8, 0] is `row.origin.x`: the offsets are walked one at a time, never added.
    println("  origin.x = {field_value(row, [8, 0]).i}");

    // The name can also arrive at runtime — from a config file or a catalogue.
    u = type_named("Row");
    if u == null { println("no such type") } else { println("found {u.name}") }
}
```

`type_of` reads its argument for its TYPE and never evaluates it — the contract C's `sizeof` has — so pass a variable, a field or a parameter rather than an expression with a side effect. `field_value` does evaluate its argument: the value is what it reads.

**A position is checked against the type's own descriptor, never trusted.** Only a field the type says BEGINS there is read; a hand-made offset, a stale one, one belonging to a different type, or the interior of a wider field all answer `OtherKind` with no read at all. And `kind` is the descriptor's answer rather than the caller's — passing the position of an `integer` field does not make the reading an integer, it makes it whatever that field is.

**A path is walked, never summed**, and that check is what keeps this from being a pointer: every step must begin a field of the type it is read against. Adding the offsets does not fail safely into "nothing here": a nested record's first field sits at 0, so `origin`'s offset plus `x`'s IS `origin`'s own and answers the enclosing RECORD. Only a non-first field's sum — `origin`'s plus `y`'s — lands in the interior and answers `OtherKind`. Every step but the last must land on an inline record — a step onto a scalar, a vector, a keyed collection or a stored reference answers `OtherKind` and reads nothing, since following a stored reference would be a pointer chase rather than a field read. A one-element path answers exactly what the bare position does, and an empty path answers `OtherKind`.

`ValueInfo` keeps three answers apart, because an ORM that confused them would write the wrong row: `OtherKind` (nothing begins there), a non-scalar kind (a nested record, a vector, a keyed collection — nothing to read out; a nested record is descended into with a path instead), and `is_null` (the scalar holds loft's null, which is not `""`, `0` or `false`).

Two limits are worth knowing before reaching for it. Reflection does not WRITE: building or mutating a value by field name is a separate and larger question. And neither half works **inside a generic body**, which is parsed once against its type variable — `type_of(v)` there can only answer with that variable, and `field_value` is a compile error rather than an empty answer, since for its main caller an empty answer is a row with no columns. Call them where the concrete type is known.
