# @F93 — Paged & remote store loading — read part of a dataset over HTTP range

## What it is

Read only the entries you ask for out of a store, instead of loading the whole file. `store_load_key` fetches one entry, `store_load_key_text` the text-keyed form, `store_load_keys` a batch, and `store_load_range` a contiguous span. Two more take a QUERY rather than a key list: `store_load_prefix` reads every entry of a `trie<T[k]>` whose key begins with a prefix — a search box — and `store_load_box` reads every entry of a `spatial<T[x,y]>` inside a bounding box — a map viewport. Both cap the WALK and not just the answer, so asking for twenty matches never pays for the rest.

The path is a local file **or an `http(s)://` URL** — the same call either way, on every target including the browser. Over HTTP loft issues `Range` requests and pulls only the 64 KiB pages the lookup touches, so a 2 GB dataset on static hosting costs a few kilobytes to query. `store_load_url_trusted` takes a whole image when you want all of it; `store_load_url` does the same pinned to a SHA-256.

## How it aids you

Ship a large dataset as a plain static file — on a CDN, S3, GitHub Pages — and query it with no database server and no API in front of it. A game streams its world chunks, meshes and sounds as the player moves; a catalogue or gazetteer answers lookups without downloading itself. Because the same call takes a path or a URL, you develop against a local file and ship against a URL with no code change.

What a bounding box COSTS is decided by the order the dataset was written, not by the box or the index. The Morton walk is symmetric and a file laid out along one axis is not, so a box crossing that axis pays for every stride it crosses. Measured on one 62 500-point grid, asking each time for the same 500 records: a 250x2 box reads 107 pages of 64 KiB where its 2x250 mirror reads 7 — and the two numbers swap when the identical data is written in the other axis order. At 107 pages the read pulls 81 % of the image to return 0.8 % of the records, which is worse than fetching the whole file once. So lay a dataset meant for viewport reads out with locality in EVERY axis: tiling it has no bad orientation, and for the square-ish boxes a viewport actually uses it beats both linear orders.

## Example

```loft
struct Part { const id: integer, name: text }

fn main() {
    all: hash<Part[id]> = [];
    store_persist_bind(all, "parts.store");
    all += Part { id: 7, name: "bolt" };
    all += Part { id: 91, name: "washer" };

    // Read back ONE entry — over HTTP this fetches only the pages it needs.
    one: hash<Part[id]> = [];
    if store_load_key(one, "parts.store", 91) {
        for p in one { println("found: {p.id} {p.name}"); }   // found: 91 washer
    }
    delete("parts.store");
    delete("parts.store.dschema");
}
```
