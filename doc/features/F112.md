# @F112 — `store_release()` — say a record is finished, and stop holding it in memory

## What it is

`store_release(collection)` says *everything I have written so far is finished*: it starts writing that out to the bound file and drops it from the process's resident set, answering with the bytes dropped. `0` when there was nothing to drop, or the collection is not bound to a file.

Content is untouched and every reference into the collection stays valid — nothing moves and nothing is freed. Reading a released record simply re-reads it from the file, one page fault later.

## How it aids you

A generator streaming a large collection into a bound store holds everything it has written, and the kernel only works out which pages are finished by evicting some wrong ones first. Saying so directly turns that cliff into a curve. Measured on a 20 000-record build, one call per record: **peak memory 44.3 MB → 2.2 MB (20×), and the wall clock does not move.**

Because it is a hint, calling it too often — or on a collection that is not bound — costs a little speed and can never cost an answer.

**Measure it while the build runs, not after.** The claim is about the working set the build holds, so it has to be sampled during the build — read `VmRSS` every few thousand records. A peak-RSS reading (`/usr/bin/time -v`, *Maximum resident set size*) reports the SAME number with and without the call, in every write shape and at every scale, and it is not wrong: the peak is set by arena growth — the store reports `cap 203 MB` holding `data 89 MB` — and a residency hint cannot lower a peak it did not cause. Sampled during a 40 000-record build, one call per record: without it `VmRSS` climbs 15.8 → 22.1 → 35.9 → 47.1 → 58.4 MB and keeps going; with it the same build holds 15.9 → 16.7 → 17.0 → 17.5 → 18.2 MB.

The wall clock is not hurt and is often helped. Same build, same 40 000 records: 6.09 s → 3.13 s where each record is returned to and its vector grows in place, and 2.74 s → 2.76 s where the record is already complete when it is inserted.

## Example

```loft
struct Tile { const key: integer, const points: vector<integer> }

fn main() {
    // A generator streaming more data than you want resident, into a store bound
    // FIRST — the file is the arena, so what it writes lands in file-backed pages.
    tiles: hash<Tile[key]> = [];
    store_persist_bind(tiles, "tiles.store");

    dropped = 0;
    for k in 0..2000 {
        tiles += Tile { key: k, points: [] };
        t = tiles[k];
        for i in 0..40 { t.points += [k * 100 + i] }
        dropped += store_release(tiles);          // this tile is finished
    }
    println("held: {tiles.len()}, dropped from memory: {dropped > 0}");

    // Nothing about the data changed. A released record is read back from the
    // file — same value, one page fault later.
    println("tile 7 still reads {tiles[7].points[39]}");

    delete("tiles.store");
    delete("tiles.store.dschema");
}
```

**It pays when records are written in key order and not returned to.** A build that keeps many records open at once relocates its growing vectors and leaves the store scattered with free blocks — 3 691 against 10 for the same data written in order — and the allocator's own free-space tree lives *inside* those freed blocks, so it keeps re-reading exactly the region the release just dropped. The same call then gives back 1.0× instead of 20×. If your generator streams in cell order this is close to free; if it does not, this is a good reason to sort it first.

Not `store_reclaim()`, which hands back the file's unused **tail** and changes its length — this changes only what is resident and never the file's size. Not a durability barrier either: it asks for writeback to *start*, and `store_durable_seal()` is what promises the bytes have landed. Unix with a file-backed store; a no-op that answers `0` elsewhere.
