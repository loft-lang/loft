# @F108 — Lazy store binding — a collection fetches on a miss

## What it is

Bind a collection to a source and stop loading it. After `store_bind_lazy(parts, "inventory.store")` the collection is a window onto that source: a lookup that **misses** fetches exactly that one entry and keeps it, so the next lookup for the same key is an ordinary resident hit. There is no separate cache to manage — the collection *is* the working set.

Two kinds of source bind the same way:

- **A store IMAGE** — a local `.store` file, or an `http(s)://` URL served with Range. Whatever `store_load_key` accepts.
- **A DATABASE** — `sqlite:<path>`, where the entries are rows in a real relational table and the `SELECT` is **derived from the collection's own type**.

Binding is per **collection**, not per store, so `persons` and `companies` can come from different sources, and two collections of the same type can bind differently. Binding replaces, and may be done before the collection holds anything.

A lookup never raises, so a bare `null` cannot tell a key that is genuinely absent from a source you could not reach — two different facts, one stable and one not. Three calls separate them:

- `store_lazy_error(c)` — why a fetch could not reach the source, or `""` when healthy. The **first** failure's reason, kept, because it names the original cause; a later, more actionable one reaches stderr but not this call.
- `store_lazy_faults(c)` — how many fetches could not reach the source. `0` is healthy; after a traversal it answers "how incomplete am I".
- `store_lazy_clear(c)` — acknowledge those faults. It is the only thing that clears them. Neither a later fetch that happens to succeed nor one that reaches the source and finds no such key does, because a traversal that missed data is still missing it — reachability now says nothing about what an earlier failure already lost.

## How it aids you

Work with a dataset far larger than memory without writing a loading step, a cache or an eviction policy. Point a collection at the source and use it like any other collection — the entries you touch are the entries you pay for, and the ones you touch twice are free the second time. Because the source can be a URL or a database, the same code queries a dataset sitting on static hosting or in a table other tools also use.

And when the data is incomplete, you find out. A traversal over an unreachable source cannot quietly answer "nothing there" — the fault count is sticky until you acknowledge it, so a partial answer cannot be mistaken for a complete one.

## Example

```loft
struct Part { const id: integer, name: text }

fn main() {
    // Stand in for a dataset you shipped earlier: a plain `.store` image.
    src: hash<Part[id]> = [];
    store_persist_bind(src, "inventory.store");
    src += Part { id: 7, name: "bolt" };
    src += Part { id: 91, name: "washer" };

    // Bind an EMPTY collection to that image. Nothing is loaded yet.
    parts: hash<Part[id]> = [];
    store_bind_lazy(parts, "inventory.store");
    println("resident: {parts.len()}");                 // resident: 0

    p = parts[91];                                      // a miss fetches this one entry
    println("{p.name}, resident: {parts.len()}");       // washer, resident: 1

    q = parts[91];                                      // a hit never leaves the process
    println("same: {&p == &q}, resident: {parts.len()}"); // same: true, resident: 1

    // A key the source does not have reads as null — and asking why tells a
    // genuine absence apart from a source you could not reach. Nothing failed
    // here, so the channel is clean.
    missing = parts[404];
    println("missing: {missing == null}, faults: {store_lazy_faults(parts)}");
                                                        // missing: true, faults: 0

    delete("inventory.store");
    delete("inventory.store.dschema");
}
```

The source is **pinned when you bind**, so a traversal sees one consistent world; if the image changes underneath, the fetch is refused and reported through the fault channel rather than silently mixing two versions. Assigning `= []` to a bound collection reclaims what it holds while keeping the binding, which is the blunt way to cap a working set.

## Binding to a database

`store_bind_lazy(persons, "sqlite:people.db")` needs no query and no mapping. The collection's own type says everything: the table is the element type's name, the columns are its fields, and the `WHERE` is its key — so `hash<Person[id]>` over `struct Person { const id: integer, name: text }` fetches with

```sql
SELECT "id", "name" FROM "person" WHERE "id" = ?
```

The database owns the schema — loft binds to tables that already exist, writes nothing, and issues no DDL. Before it answers anything it checks once that the columns are there and that an **index** actually serves the lookup, because a missing index is not an error: it is a silent collapse from lazy to table-scan.

Two calls cover what a key cannot express. Both pull rows INTO the collection, so a record found either way is the SAME record a keyed lookup finds:

```loft
// One query, many rows — the cure for fetching 100 records one at a time.
got = store_lazy_range(events, 100, 199);

// A predicate the key cannot express. Written down, so the cost is visible.
found = store_lazy_query(persons, "name LIKE 'Ada%'");
```

Because the collection is the working set, `len(c)` is the RESIDENT count and iteration walks what has been touched — never "what exists in the table". A slice never fetches; ask for a range explicitly.

The companion feature is `store_load_key` and friends (#93), where you say explicitly which entries to fetch; this is the same machinery driven by the lookups themselves.
