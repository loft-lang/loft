# @F109 — `#superseded` — steer callers to a newer form without breaking the old one

## What it is

Sometimes a better way to write something arrives after the old way has already shipped.
loft never answers that by removing the old way — a program that works keeps working. So
instead it gives you a way to *point at* the newer form.

`#superseded "Y"` on a function says: this is superseded by `Y`. Anyone calling it sees a
note naming `Y`, and the old form keeps working exactly as before, for good. It is a
signpost, not a removal, and there is no later version in which it becomes one.

Two rules keep the signpost honest, and loft checks both every time it compiles:

- **The successor has to exist.** `#superseded "no_such_thing"` is a compile error
  (*"the steer would ship dangling"*), so a signpost can never point at nothing — when the
  file is built as a program. Under `loft test` that check does not run today (loft#985),
  which is worth knowing because a library's CI is a test run.
- **The old form has to call the new one.** The superseded function becomes a thin shim
  over its successor rather than a second implementation of the same idea. If its body
  never calls the successor, loft says so — because two separate implementations drift
  apart, and then the note is sending readers somewhere that behaves differently.

The note reaches only the person who can act on it. It appears when the call is in the code
you are compiling, and stays quiet when the call is inside a library you merely depend on —
being told to modernise someone else's code is noise you cannot do anything about.

## How it aids you

You can improve a library's shape without splitting its users into those who upgraded and
those who did not. Everyone's existing code goes on working; the people writing *new* code
learn the better form at the moment they would otherwise have copied the old one.

And you learn about the improvement from your own compiler, at the call you actually wrote,
rather than from a changelog you had to think to read.

For the reader of a codebase the value is the reverse: a name marked this way tells you it
is settled history, not a live choice you are expected to weigh against its successor.

## Example

```loft
// The successor — the form to use now.
fn scaled(v: integer, by: integer) -> integer { v * by }

// The old form. It keeps working, and its body is a shim over the successor.
fn doubled(v: integer) -> integer { scaled(v, 2) }  #superseded "scaled"

fn main() {
    println("{doubled(21)}");    // 42 — the old form still works, unchanged
    println("{scaled(21, 2)}");  // 42 — and the successor gives the same answer
}
```

Compiling this points at the call on the first line of `main`:

```
advice: `doubled` is superseded — use `scaled` (the old form keeps working)
```

Set `LOFT_NO_STEER` to turn the note off.
