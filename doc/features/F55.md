# @F55 — Package management (`loft install`, `loft.toml`, lockfile)

## What it is

loft's package manager. `loft install <name>` downloads a library from the registry and installs it for use; a `loft.toml` file records the packages your project depends on, and `loft.lock` pins each one to an exact version so builds stay reproducible. `loft new <name>` scaffolds a fresh library, and `loft update` refreshes the pinned versions. A single-file script belongs to no project, so it gets the same pin from `loft pin <script.loft>`, written beside it as `<script>.loft.lock`.

## How it aids you

You reuse other people's libraries instead of reinventing them, and the lockfile means the versions you tested are the versions everyone else — and your CI — gets. Declaring dependencies in `loft.toml` keeps a project's requirements in one place that travels with the code.

**The two files do different jobs, and only one of them is the pin.** `loft.toml` records a CONSTRAINT (`random = "0.1.0"`); `loft.lock` records the RESOLUTION, and the lock is what resolution reads. Each `[[package]]` block carries five fields — `name`, `version`, `url`, `sha256`, `source` — so what travels between machines is an artifact rather than a label. The SHA-256 is what makes reproducibility a claim about bytes.

**A declared dependency is not yet a pinned one.** Until `loft install` resolves the constraint into `loft.lock`, the project carries no answer of its own and the resolver falls back to what the box can offer. `advice[undeclared-dependency]` reports the sharper form of the same gap — a `use` that resolved a registry package the manifest never declares at all, so nothing distinguishes *"we depend on this"* from *"this happens to be installed here"*, and the negative gate *drop the dependency and the tests must stop compiling* cannot be written.

**What no field pins is loft itself.** A perfect pin and a broken build are compatible states: a project pinning a release built against an older loft resolves exactly the release it asked for, and can still fail on a rule loft has added since. `[package] contract` is the field that warns about that (`warning[package-contract-drifted]`) and it is optional, so a package released before it says nothing at all.

## Example

```
$ loft new mytool                  # scaffold loft.toml + src/ + tests/
$ loft install markdown            # fetch a library from the registry, and record it
$ loft install markdown@1.2.0      # or pin a specific version
$ loft install                     # resolve every dependency the manifest declares
$ loft update                      # refresh the lockfile to the latest allowed versions
$ loft pin script.loft             # pin the libraries a single-file script uses
```
