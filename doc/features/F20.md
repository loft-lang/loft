# @F20 — Variant-based dynamic dispatch

## What it is

When a value can be one of several shapes — a Shape is either a Circle or a Rect — you write one version of a method for each shape, all with the same name. Loft runs the right one automatically, based on which shape the value actually holds.

## How it aids you

You call `shape.area()` and get the correct answer without checking which kind of shape it is yourself. Add a new shape later and you simply add its version of the method — the code that does the calling stays exactly the same.

## Example

```loft
enum Shape {
    Circle { radius: float },
    Rect { width: float, height: float }
}
fn area(self: Circle) -> float {
    3.14159 * self.radius * self.radius
}
fn area(self: Rect) -> float {
    self.width * self.height
}
fn main() {
    shapes: vector<Shape> = [
        Shape::Circle { radius: 2.0 },
        Shape::Rect { width: 3.0, height: 4.0 }
    ];
    for s in shapes {
        println("area = {s.area()}");   // area = 12.56636, then area = 12
    }
}
```

## Every variant is covered

The compiler checks that every shape is covered. When a value is typed as the enum — an element of a `vector<Shape>`, a `Shape` parameter — a call needs a method for every variant. Add a `Tri` variant without its own `area`, and the call is a compile error: *"call of `area` on `Shape` is not exhaustive — missing: Tri"*. Either write `fn area(self: Tri)`, or write one fallback on the enum itself, which every variant without its own method reaches:

```loft
fn area(self: Shape) -> float { 0.0 }   // covers every variant that has no `area` of its own
```

The choice can depend on two values at once — `hits(a, b)` with a definition per pair of variants. That is multiple dispatch (@F122).
