Performance

Key takeaways

The four loft execution modes have very different performance profiles depending on what the program does.

loft interpreter vs Python

The interpreter runs your program without a separate compilation step. Loft is statically typed, so the interpreter never checks the type of a value at run time; its cost is dispatching each bytecode operation and reaching collection data through the store layer. It is slower than CPython on these benchmarks: close to it on an integer loop and on string building, several times slower on hash lookups and float kernels. For hot code, compile with --native.

loft native vs Rust

The native pipeline compiles loft source to Rust via --native or --native-release, then invokes rustc. For floating-point kernels the generated Rust is as fast as hand-written Rust (Mandelbrot 1.01×, dot product 1.06×), and so is trial division (sieve 1.02×). Integer loops run about 2× (sum loop 1.81×, Collatz 1.99×), because loft integer arithmetic is checked: an overflow answers null instead of wrapping. Newton sqrt (2.21×) pays the same for its float division, whose result may be null. Recursion (Fibonacci 3.14×) and collection-heavy code (word count 3.55×, insertion sort 3.81×) are the widest gaps.

loft wasm vs loft native

The wasm build compiles the same generated Rust for wasm32-wasip2, so it runs everywhere wasmtime or a browser is installed. Arithmetic runs close to native speed; text building trails native most, because every text allocation goes through the allocator inside wasm linear memory. Wasm is a good target when native compilation is unavailable.

Bottlenecks

Interpreter — bytecode dispatch The interpreter executes bytecode. The most frequent operator shapes — an integer operator over locals, a compare-and-jump, an element read of an integer vector, the step of a text walk — run as one fused instruction, and every other operation is one dispatch. There is no just-in-time compiler (JIT). Each iteration of a tight loop pays this per-instruction cost.
Native — collection access through the store layer Hash lookup (word count: 3.55×) and indexed vector reads and writes (insertion sort: 3.81×) go through the helpers in src/codegen_runtime.rs. They perform bounds checks, null-sentinel tests and store-pointer indirections that hand-written Rust avoids.
Native — function call overhead for recursive code The recursive Fibonacci benchmark runs at 3.14× hand-written Rust. The generated code passes the stores and other runtime context through every call frame, also for a function that does not touch the heap.
Native — checked integer arithmetic Integer overflow answers null rather than wrapping, so every integer operator checks its result. Counted loops run their index arithmetic unchecked behind one guard; straight-line arithmetic stays checked.
wasm — text allocation Text in the wasm build is a Rust String allocated inside wasm linear memory, which grows with memory.grow; each append that reallocates costs more than it does natively.

Open performance work

  • Native collections without the store layer — emit direct Rust Vec / HashMap operations for collections whose ownership allows it, instead of codegen_runtime helper calls.
  • Native calls without the stores — the compiler knows which functions are pure, and their generated code takes the stores parameter all the same.
  • Unchecked integer arithmetic — where the operands are provably non-null and cannot overflow, emit plain Rust arithmetic.
  • wasm text representation — a string layout for the wasm target that closes its gap on text building.
