# Release process — the record

The dated measurements and incidents behind the rules in [RELEASE.md](RELEASE.md) and
[RELEASE_PUBLISH.md](RELEASE_PUBLISH.md).  Those docs state each rule as it holds now; this
file keeps what justified them, oldest first.  What a PARTICULAR release needed and decided is
its cycle directory under [releases/](releases/README.md), not this file.  A record doc: its
dates and hashes are the point.

## Cycle themes of the first calendar cycles

- **`2026-07`** — stability, the package registry and library hardening (extraction
  finished, registry maintenance and discovery, reproducible packaging).
- **`2026-08`** — "become a better PHP": the server-side web and database stack — the `#c`
  direct-C-ABI tier (@PLN24), the MariaDB/PostgreSQL clients (@PLN23) and the real HTTP server
  (@PLN4) ([BROADENING.md § Better PHP](BROADENING.md#better-php--the-2026-08-cycle-theme)).

From `2026-09` on, a cycle's theme is recorded in its own `releases/<cycle>/README.md`.

## v2026.7.0 — a release published before its binaries

The pre-2026.7 flow created and published the release in one step.  Publishing creates the
tag and freezes the release; under the org's immutable releases the later upload was
rejected, and v2026.7.0 shipped without binaries.  Source of the draft-first pipeline.

## 2026-07-31 — reproducible builds, the path half

1. The published v2026.7.2 binary embeds `/rustc/8bab26f4f68e0e26f0bb7960be334d5b520ea452`,
   byte-for-byte the local stable 1.97.1: the compiler was already pinned by
   `dtolnay/rust-toolchain@stable` plus `Cargo.lock`.
2. Absolute build paths were the blocker: the release binary carried
   `/home/runner/.cargo/registry/...`, a local build the local home — **192 occurrences**.
3. `[profile.release] trim-paths` was unstable in Cargo 1.97.1 and refused to parse.
4. `--remap-path-prefix` took 192 → 2 on stable rustc.
5. The last 2 were `build.rs` exporting `LOFT_BUILD_RUSTFLAGS` verbatim, so the remap flags'
   own text was baked in.  Hashing it away was proposed after reading only the `cache.rs`
   consumer and disproved the same day by the other one: `extensions.rs` passes the string to
   child cargo builds so a shared dependency's SVH matches loft's own (#274); a `u64` breaks
   `--native` at link with a colliding `StableCrateId`.  The toolchain path accounted for 31 of
   the 192.
6. A GitHub artifact is `x86_64-unknown-linux-musl`; a local `cargo build --release` is
   `-gnu`, so a comparison needs `rustup target add x86_64-unknown-linux-musl` and
   `musl-tools` first.

## 2026-08-16 to 2026-09-04 — the nightly schedule is not a clock

The 03:00 UTC daily started anywhere between 03:34 and 14:45, on whatever `main` was then.
Source of "prove the nightlies on the candidate's commit".

## 2026-08-31 — the registry splice had never been completed

The signed index carried 42 library packages and no `loft` package, so `loft self-update` had
never had a release to resolve and `loft verify-self` had never answered its signed-index
question anywhere.  The 2026.8.0 submission had been attempted and rejected by the registry's
own validator, which had no toolchain case: gate 3 re-packages a source tree with
`loft package`, and loft's root has no `loft.toml`.
[registry#22](https://github.com/loft-lang/registry/pull/22) (gate 2b plus a narrow gate-3
exemption) and [registry#31](https://github.com/loft-lang/registry/pull/31) (`loft 2026.8.0`,
the first toolchain entry) merged and were signed; `self-update --dry-run --refresh` then
answered `2026.8.0 is the newest release`.  The chain was verified end to end in a throwaway
clone: #22's validator passed all four gates on the spliced entry, the old validator reproduced
the original failure, and the entry regenerated by `gen-toolchain-entry.py --splice-into` was
byte-identical to the one the release attached.  Order learned: the entry must land before the
version-bump PR can merge, because `check-release-published.py` gates that PR.

The same audit found `scripts/install.sh` copying `bin/` and `default/` only and then handing
`verify-self` the whole bundle's manifest, so every installation it made ended in *the
installation does not verify*.  2026.8.0 shipped that way, and the by-hand item did not catch
it; the only path anybody had smoke-tested was a fresh git clone, not the zip users download.
@PLN156 then turned step 4's effects into automatic checklist items and gave every item a
cadence, because 2026.8.0's real cost was discovering by hand that several "done" things had
never been true.  Before `make release-checklist` there were three overlapping partial lists
in RELEASE.md, and the steps in none of them — the Windows `self-update`, the registry splice,
`install.sh` — were the ones skipped.

## 2026-09-04 — the clippy suppression census (`e4366d4d`)

257 attributes named a clippy lint (244 on items, 13 file-scope, 3 via `cfg_attr`); 329 lint
mentions over 54 lints.  150 of the 244 item-level attributes had a justifying comment.
**Dead:** 51 outright and 7 in part — 66 of the 329 mentions (`too_many_lines` 16,
`too_many_arguments` 15, `unused_self` 5, `cast_precision_loss` 3); 34 of the dead ones carried
a justification describing a constraint that no longer existed.  **Redundant with a crate
root:** 80.  **What CI never lints:** 10 pedantic warnings with debug assertions ON, 7 in the
browser wasm rlib.  **Outside the census:** 167 `#[allow]` naming only rustc lints, 111 dead in
every compiled leg.

## 2026-09-05 — the bundle smoke is the walkthrough

The owner ruled that the tag pipeline's per-bundle smoke is the cross-platform hands-on
walkthrough.  `M-hands-linux` / `-macos` / `-windows` were retired on 2026-09-23; what they
added that no runner observes (Gatekeeper on an unsigned download, the VS Code grammar symlink
on Windows) no release had ever recorded.

## 2026-09-10 — two install layouts (loft#1497)

`self-update` over a prefix once source-installed wrote a `default/` nothing loads, and the
older `share/loft/default` kept winning: a 2026.9.0 binary read a 2026.8.0 standard library on
two machines, `verify-self` passed throughout, and `println("hello")` died with SIGSEGV in
`OpFreeText`.  A third machine, built from source, ran the program fine — the control that
placed the split on install method, not release.  `verify-self` had its own spelling of the
resolution rule until then (loft#1499).

## 2026-09-07 to 2026-09-15 — reproducible builds, the C-toolchain half

`scripts/repro-flags.sh` closed the path half without a container, and the weekly
`repro-build.yml` rebuilt v2026.9.0 for `x86_64-unknown-linux-musl` byte-identically.  The
MSVC and `aarch64-apple-darwin` legs stayed red (09-07, 09-14) on CODE, not paths: the MSVC
rebuild had `.text` 384 bytes smaller and four fewer `.pdata` entries.  `ring` builds C
through the `cc` crate with the runner image's compiler; on one Windows runner the default
toolset (14.51) linked `.text 0xbd1586`, `-vcvars_ver=14.44` linked `0xbd1656`, and the
published binary (an image two weeks older) had `0xbd1706`.  A Windows link was also not
deterministic: two builds from one root differed in 12 bytes (TimeDateStamp, its debug copy,
the PDB GUID); `/Brepro` alone left 20 bytes differing, and `/DEBUG:NONE` made them identical.

## 2026-09-23 — waivers, row classes, retirements

Before waivers, three of three release-gate runs ended red, every time on environment legs:
the Windows `Test` leg (red or cancelled on 11 of the 14 nightlies to 2026-09-23, loft#1652),
the macOS and Windows repro legs, and a registry package's own defect (`hex_fit` on
2026-09-08, `imaging` on 09-23 through `registry-validation`, since removed from the gate).
2026.9.0 proceeded on hand-run substitutes with a 90-minute run proving nothing.

The same day the rows were split into GATE, `[report]` and DERIVED classes, because "21/27
done" with them mixed said nothing about what was blocking; and a tick began recording its
commit, because 2026-09's candidate ticks named `e77ef442` while the tag was `b1016d00` and
only a by-hand diff showed nothing shipped had moved.  Retired: `M-leaks` (the suite's own
assertion), the three hand walkthroughs, and `M-install-live` (`scripts/acquisition-chain.sh`
installs a library with the acquired binary).

Carrying the sweeps under `[mid]` had made the halfway view read `7/12` against a denominator
no halfway run could reach; they became `[cand]`, run early and counted nowhere.

## The file-split row

`M-file-sizes` had been a report read once per cycle; nothing acted on it and `src/` reached
18 files over 6 000 lines, so the split became the gate row `M-file-split`.
