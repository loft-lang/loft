# Handoff 2026-11-05 — a true 32-bit Tanmatsu build, and the way to 60 fps

One session, on the Mac (`Jurjen-Stellingwerffs-Mac`), with a Tanmatsu on USB.  It continued
[@PLN217](https://github.com/loft-lang/plans/issues/217) (one source, two widths), ran
`tile-world-game` on the device as a 32-bit build, measured why it is slow, and ended in a new
plan, [@PLN218](https://github.com/loft-lang/plans/issues/218), plus owner rulings on
[@PLN216](https://github.com/loft-lang/plans/issues/216) and @PLN209.  Read the two plans first.

## Owner rulings this session (in the plans)

- **The engine is C, the game is loft** — the split of a 3D engine; the main reason is one set
  of abstractions for 2D and 3D (`stage` above both engines).  PLN209 API.md, @PLN216 § The
  engine boundary, @PLN218.
- **Memory regions never appear on the loft side** — no API, flag or preload hint names fast or
  slow memory; placement is the engine's decision.
- **The landscape is drawn when it changes, the actors every frame**; a thing is landscape while
  it rests, an actor while it moves; tall landscape pieces in front of actors are redrawn over
  them; the engine keeps what is read every frame in fast memory by itself, "most, not all".
- The plan change is driven by today's hardware findings (@PLN216 § Why the plan changed).

## Measured on the Tanmatsu (32-bit build)

| | |
|---|---|
| a loft vector element write / read | ~470 ns / ~120 ns (the same for 4 KB and 768 KB) |
| `(a * 3 + i) & 65535` loop | ~60 cycles an iteration, `i32` and `i64` alike |
| `single` vs `f64` mul-add | 12 ms vs 74 ms for 200k |
| `game::draw` at 208x160 | 160 ms, 133 ms after hoisting its allocations (host A/B 429 → 301 µs, frame checksums identical) |
| `game::draw` at 800x480 | 347 ms → 318 ms |
| `game::update` (16 ms tick) | 5.1 ms |
| `tiles::pixels` / `screen::show` at 1x | 3.2 ms / 16 ms |
| `screen::poll(15)` | sleeps 15 ms per frame |
| the game, end to end | 64-bit 2.3 fps, 32-bit 2.5 fps |

The host profile of `game::draw`: 99 % per-cell logic, 4 % pixels; ~44 % hash probes
(`tile_world`'s chunk hash per cell read), and allocation inside the loops (since hoisted).

## Open, in order

1. **The `-O2` build hangs on the device.**  loft's C at `-O2` instead of `-Os` (and with a
   256 KB main stack): no console line at all, the console port drops every 20 s.  Next: panic
   output (`CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT`), watchdog on, then `-O2` on the runtime only.
2. **@PLN218 S1: the SRAM budget** and the primitives on the device (`kit/bench.loft` extended).
3. **The library branches:** run each library's testbed (LIBRARY_AUTHORING.md § The testbed),
   then PR + auto-merge.  Confirm the screen's orientation by eye after the `screen` rotation fix.
4. **Report the game's changes** to its agent, with `kit/tile-world-game-width32.diff`: cell keys
   and hashes in `i64`, `Timing.since: i64`, allocations hoisted out of `draw` (an `Ids` struct,
   `Ground` and the shade buffer kept in `Game`), composing at 1x in `main.loft`.
5. **loft defects found, not yet fixed or filed** (verify on `origin/main` before filing):
   - a file's own private struct declared below its first use loses to a used library's private
     struct of the same name: "type is private" (4-line repro: a library with `struct Inner`, a
     program using `Inner { … }` before its own `struct Inner`);
   - a loop over a `hash` builds and sorts a copy every time (`loft_hash_sorted` mallocs per loop);
   - a C program that truncates a pointer handle exits with status 1 and no message;
   - the C runtime's index math is `int64_t` (`loft_vh_index`), and at `-Os` `LOFT_HOT_INLINE` is
     not forced, so an element write is three calls (@PLN217 S4).
6. **`find_problems.sh --changed`** reported 31 failures but was cut off by its time limit; this
   Mac's `rust-objcopy` cannot load `libLLVM.dylib`, which may explain some.  Triage before a PR.
7. **The audio task on the device** logs `i2s_channel_reconfig_std_clock: invalid state` at start;
   sound probably does not play.
8. **`c_sweep.py --wasm` on macOS** needs `kit/wasmcc` (Homebrew clang 23 wants `wasm32-wasip1`
   and explicit sysroot paths); fold that into `c_sweep.py`.

## This Mac's setup (outside git)

- ESP-IDF v6.0.3 in `~/.espressif` (`install.sh esp32p4`); `brew install cmake ninja` (ESP-IDF on
  macOS), `llvm lld wasi-libc wasi-runtimes` (the wasm32 leg).
- badgelink: `git clone https://github.com/badgeteam/esp32-component-badgelink`, in its `tools/`
  `python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt`; run it with
  `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib` (Homebrew's libusb).  The device must be in USB
  mode: the purple diamond key on the launcher.
- The console: `kit/tlog.py <logfile>` follows `/dev/cu.usbmodem*` and reopens on restart.
- The build: `LOFT_WIDTH=32 loft --native-esp <dir> --lib libs main.loft` from the game's
  directory, with its libraries fetched as its `fetch-libs.sh` names them.
