## The owner's rulings this arc stands on

1. **C77 amended** — what a Rust programmer writes with `&mut` is admitted in its `&` spelling,
   ahead of C77's narrowing (slot cursor; a slot handed to a function).  Before proposing a
   refusal of a `&` shape, ask "would a Rust programmer write this with `&mut`?".
2. **Natural code first** — the spelling users write is the one to make work and fast.
3. **Users' own data structures** are the gap this arc fills; rank work on them high.
4. **The prime goal is programs that expose the cost** (phase B).  Making them fast is the
   ordinary portal loop (`loft-optimize`), not special to this plan.

## Next: P1 — the `&` parameter regression (known broken on the pushed branch)

`bind_slot_link` fires on a `&` PARAMETER once it is re-pointed (`slot = &slot.left`), so a whole
write that runs before any re-point goes to an unset slot local.  Repro (the interpreter panics
with "a NULL DbRef reached a store accessor"; `--native-c` answers `80 4`, should be `80 3`):

```loft
struct Tree { k: integer, left: Tree?, right: Tree? }
fn size(t: Tree?) -> integer { if t == null { return 0; } 1 + size(t.left) + size(t.right) }
fn take_min(slot: &Tree?) -> integer {
  while slot.left != null { slot = &slot.left; }
  k = slot.k!;
  slot = slot.right;
  k
}
fn main() {
  t = Tree { k: 50, left: Tree { k: 30 }, right: Tree { k: 70, right: Tree { k: 80 } } };
  n = &t.right.right;
  k = take_min(n);
  println("{k} {size(t)}");          // 80 3
}
```

Interim fix: skip arguments in `note_slot_link` / `bind_slot_link`
(`self.vars.is_argument(var)`), so the parameter keeps its old path; a suite cell for the
zero- and one-iteration cases on both backends.  The old path is itself wrong for a null write
on entry — `fn clear(slot: &Tree?) { slot = null; }` given `n = &t.left` leaves the tree whole —
which is phase P's (the exact link), not P1's; keep that cell out of P1 or mark it.

## Then: B — the bench programs

The plan's table: `22_expr`, `23_lru`, and three routines on `21_tree` (`build_rec`,
`enum_list`, `lookup_copy`).  How a bench is made here:

- Layout and row format: `bench/21_tree/bench.loft` + `bench.rs` (the Rust twin) are the model;
  one op per repetition, keys varying in value not work (`key(i, salt)`, the LCG), `--n N`, the
  `row(...)` printer.  Register in `bench/portal/routines.tsv` and `classes.tsv`, a row in
  `bench/README.md`.
- Hashes: every lane prints the same `hash`; check them against an independent Python run of the
  same algorithm (21_tree's four were: `d0fc3f4 829a302c 41ceb783 3b0656d6`).
- Measure: `python3 bench/stats.py --only 21 --lanes rust,c,interp`.  Read the emitted C:
  `loft --native-c --native-emit out.c bench/21_tree/bench.loft`.
- `delete` and other stdlib names are reserved: a routine called `delete` fails to compile.
- `cur: Tree? = t` COPIES the tree (`(B-Copy)`); a walk that writes needs `&`.  That copy is
  exactly what `lookup_copy` is meant to expose — write it that way on purpose.
