# @PLN146 W2 — the parser, the basic marks, and the rasteriser they had to borrow

The phase gate for **W2**, and the three findings that decided how it is built.
The plan and its other phases are in [README.md](README.md); the corpus and the
grammar this owes are [W0.md](W0.md).

## The gate

```sh
corpus/w2.sh              # render the W2 subset in loft, diff against golden/
corpus/w2.sh --control    # …with a one-pixel error injected; the diff must see it
probes/w2_raster.py       # the unit-level half: 335 shapes against Pillow directly
```

**28 of 28 scenes, 0 pixels different — on BOTH backends.** 29.8 s compiled, roughly
eight minutes interpreted; the gate defaults to `--native` and `W2_BACKEND` overrides
it. The control turns all 28 red. The package's own suite — 23 tests, no Python — is
green on both backends too, which is where the `single` arithmetic gets its second
reading.

The subset is **computed from the scenes, not listed**: a scene qualifies when it
uses only what W2 owes. So a scene that gains a `Fronds` line leaves the gate by
itself and one that loses its last gradient joins it, and the gate cannot quietly
stop covering something. Today that is 28 of the 37; the nine outside it are the
`Fronds` scenes and the two with gradient fills, which are W3 and W4.

The comparison is on **decoded pixels**, not file bytes. Two PNG encoders agreeing
byte for byte is a different and much weaker claim than two renderers agreeing —
and one of the 28 (`old_woman`) is an RGB image where the other 27 are RGBA, so a
byte diff would have had to special-case the one scene that exercises the opaque
path.

## Finding 1 — `graphics::fill_polygon` answers a different question

W1 shipped `fill_polygon` under a gate that says it agrees with `fill_triangle`
pixel for pixel, proved by a 15 625-triangle sweep. W2's gate says the fill agrees
with `draw.py`. **Those are not the same gate**, and the discovery cost one probe:

| | agree with Pillow |
|---|---|
| `graphics::fill_polygon`, 400 random polygons | **4** |
| `graphics::fill_polygon`, W1's own reference triangle | 35 px differ |

Neither rule is wrong. `fill_polygon` interpolates each crossing in INTEGER
arithmetic and fills an inclusive span between a pair of them; Pillow fills the
pixels whose **centres** are inside, in 32-bit float. The second is arguably the
better rule — but `fill_polygon`'s is a published, gated contract with `fill_triangle`
on the other end of it, and a `.draw` scene is *defined* by what the oracle renders.

So the Pillow rasteriser is ported into `drawing` itself
([`raster.loft`](https://github.com/loft-lang/loft-libs-graphics/blob/main/drawing/src/raster.loft)),
public, and `graphics` is untouched. Three things in it look like mistakes and are
the contract, so they are reproduced verbatim: a horizontal edge is drawn as its own
span and takes no part in the crossings; an edge ending on a row contributes its
crossing TWICE unless the row is the polygon's last; and the "connect discontiguous
corners" repair writes back to `xx[k]` where `k` is an **edge** index rather than a
crossing index, so it can move a crossing belonging to a different edge.

## Finding 2 — the 32-bit float is load-bearing, not incidental

`Draw.c` keeps `Edge.dx` and the scanline crossing array in C `float`, and two
**exact-equality** tests read that rounding: *is this crossing an integer?* and *do
these two edges cross at the same x?* Both gate the corner repair, so the rounding
decides whether a span is moved.

Measured, before any loft was written: a faithful model in double precision matches
Pillow on **488 of 500** random polygons. The 12 are not near-misses — a moved span
is tens of pixels. Every value that is a C `float` there is a `single` here, and
loft's `single` is per-operation binary32 on both backends (probed: the edge
`(36,46)-(-1,2)` crosses y=2 at exactly `-1.0`, which is what fires the repair).

Re-run against the real port, widening those values to `float` turns **4 of 335**
cross-check cases red.

## Finding 3 — `ROUND_DOWN` puts the sign outside the `ceil`

```c
#define ROUND_DOWN(f) ((int)((f) >= 0.0 ? ceil((f)-0.5F) : -ceil(fabs(f) - 0.5F)))
```

So `ROUND_DOWN(-0.45)` is **0**, not -1. Take the obvious `ceil(f - 0.5)` and a span
that should end on column 0 ends on column -1, clips away, and draws nothing.

This one is invisible on a case set that stays on the canvas — a crossing only goes
negative when the shape hangs off the left edge. The first version of the probe had
90 fewer off-canvas cases and the naive rounding turned **1 of 245** red; with them
it is 2 of 335, and the same defect was what made the very first model disagree with
Pillow at all. *A control that barely fires is a case set that barely covers.*

## What this build does not draw

`grad=` / `radial=` fills (W3) and the `Petals` / `Fronds` arrays (W4) **parse** —
so they cannot fall through and be misread as something else, which for `Fronds` would
mean `Line`'s pattern finding the two coordinates on the line and drawing a segment
nobody wrote — and each is listed in `Sketch.deferred` with its line. A caller knows
the picture is short of a mark rather than finding out by eye. A line no command
accepts at all is a different thing and lands in `Sketch.unparsed`.

`check` and `landmark` are read and carried; the report channel that acts on them is
W5.

## Smaller things worth carrying forward

- **The parsed scene is a `Sketch`, not a `Scene`.** `mesh3d::Scene` owns that name
  and `graphics` depends on mesh3d, so the collision is a hard compile error — the
  same trap W1 hit with `Point` / `Coord`. The 3-D names reach further into 2-D
  code than they look like they do.
- **The command dispatch order is `draw.py`'s and is not tidy** — `Circle` is tried
  before `Poly`, `Line` last of all. A grammar this loose is defined by the order its
  alternatives are tried in, and re-sorting it silently re-reads lines that sit in
  two alternatives.
- **`grey(L)` rounds half to EVEN**, because `draw.py` uses Python's `round`. `fill=0.5`
  is 128 and not 127 — one level, which no eye would find and a byte diff would. No
  corpus scene uses `fill=`, so this is a difference nothing would have caught; it is
  pinned by a test rather than left to be discovered by W3's first grey scene.
- **`ImageDraw.line` splits at width 1**: wider is a filled quad, width 1 (or 0) is a
  Bresenham walk that stops one pixel short, with `draw_lines` putting the last pixel
  back afterwards. Route a width-1 line down the quad path and 8 of 245 probe cases go
  red — which is how the split was found, as a probe bug rather than a port bug.
- **Cost:** the whole 28-scene subset is 29.8 s on `--native` and roughly eight minutes
  on `--interpret` — same 28 scenes, same 0 pixels. The gate defaults to `--native`
  (`W2_BACKEND` overrides) and W6 should assume the same. The work is the fill: a
  256x256 scene is drawn on a 768x768 canvas and every filled span is written pixel by
  pixel, so the cost tracks ink rather than marks.

## Shipped as a package

`drawing` 0.1.0 — [loft-libs-graphics#43](https://github.com/loft-lang/loft-libs-graphics/pull/43),
merged, released as `drawing-v0.1.0`, and published to the registry (`ac55480`).
`loft install drawing`.

Publishing it is what turned the registry signer into something an agent can
drive: `registry_maintain.sh --only drawing` now publishes exactly the named
libraries and hands the signer `--expect drawing@0.1.0`, so a run that changed
anything else refuses instead of signing it. See
[PKG_REGISTRY.md § The third route](../../PKG_REGISTRY.md#the-third-route----expect-a-confirmation-that-checks).

Targets are measured rather than claimed: interpreter and `--native` are gated;
`--native-wasm` fails on `graphics`' glutin/GL crate, which is not wasm-clean;
`--html` compiles and the whole render path is pure loft, but no headless-page
test runs yet, so the README says "should work" rather than "measured".

## What W3–W6 and @PLN147 inherit

`Paint` already carries `Linear` and `Radial` with their `dir=` / `at=` specs parsed,
so **W3 is two draw paths and no parser change**. `smooth_pts` / `smooth_vals` and the
ribbon are what `Fronds` needs for its curved, tapered strokes, so **W4 is the array
placement and the seeded field, not the drawing**. `Sketch.checks` / `Sketch.landmarks`
are already collected, so **W5 is the evaluator and the exit contract**. `render()`
answers a `graphics::Canvas`, which is what `assets`' packer takes, so **W6 needs no
PNG in between** — which was its whole point.

@PLN147's `X1` extends this oracle gate across targets; the thing to extend is
`corpus/w2.sh`, and the thing that makes it extensible is that its subset is computed
rather than listed.
