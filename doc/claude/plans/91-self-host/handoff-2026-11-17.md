## The first thing to do

1. **A background job may still be running** in the tested tree (`loft2`): it re-pins the
   runner and writer baselines at the current suite pin, layer by layer, and ends with a line
   `ALLDONE` in its log.  Its log and the script are in the session scratchpad the memory note
   names (`repin.out`, `repin.sh`).  While it runs: no `cargo` build, no change to that tree.
   When it has ended, commit `selfhost/bench/run_image_survey.baseline.tsv` (and
   `bgen_survey.baseline.tsv` if it moved) in a commit that says the suite pin moved and that
   nothing differs — the block figures are the table above.  If it was killed, run the layers
   again: `LOFT_SUITE_DIR=<a suite clone at tests/loft-suite.pin>
   python3 selfhost/bench/run_image_survey.py [--written] [--functions] --jobs 5
   --write-baseline selfhost/bench/run_image_survey.baseline.tsv` (about 25 minutes a layer,
   light on memory), then `bgen_survey.py --write-baseline …`.
2. **Promote the new work**: `tuxedo-pln204-next` (`loft2-next`) is one commit past the tested
   line — the match over an iterator, `c4582ce53`.  Fast-forward `tuxedo-pln204-int32` to it,
   push, and tell the tester the tip and what to watch (a yield of an existing struct-enum value

3. **Rebase after PR #2540 merges** (loft3 opened it with the cut `d5aa51b50`): replay

## Before more case work — the instruments

[front-end-instruments.md](front-end-instruments.md) is the design of three things that make
the rest of the port fall into place, measured before it was written: run what gate E agrees on
from the loft front end's own definitions (no such path exists yet), give verdicts and a

design on 2026-11-17; it is not built.

## Working mode

Two worktrees: `loft2` on `tuxedo-pln204-int32` is the TESTED line, `loft2-next` on
`tuxedo-pln204-next` is new work; promote by fast-forward.  The tester (another machine)
watches the tested line, runs the development gate per tip and the real gate on clean tips, and
reports: the gate line, each differ reduced with its mint order, a "next three moves" block
with Rust's `defs` section, a FAMILIES count for families asked for, and a pre-audit of whether
a port's tests already exist.  A cell is added only on a thin verdict or to pin an order.
The gate workflow triggers on pushes to `elab-gate`, which the TESTER makes: a hold asked by
loft3 must be relayed to the tester.

Before pushing a change to a SHARED rule (schema row order, the return-buffer handover, a
staging loop every literal runs), sample about forty programs on the probe: two such fixes cost
nine agreeing programs for one cycle on 2026-11-17.

## What landed on 2026-11-17 (front end)

Generics slices 5–6, `insert` / `reverse`, tuples holding a record and the whole-tuple copy,
closures capturing a loop local, omitted nullable fields, comprehensions into a struct field
and of text / record elements, key ranges over a sorted or an index, keyed writes that read
their collection, guards on vector match arms, the cursor match and most of the rule grammar
(sub-rules answering a record or an integer, declared above or below; optional and repeated
sub-rules with a separator; a repetition of plain elements), the literal-rebuild family
(staged scalars and texts, the view, the snapshot by copy, the demote of a return buffer, a
literal into a place that reads it), capturing lambdas in a returned literal's field, a
function value copied out of a field, the match over an iterator.

Three Rust front-end fixes by the tester are on the branch and in PR #2540: loft#2534 (a stack
overflow), loft#2535 (the return-buffer handover no longer depends on a newline), loft#2536
(a call that reads the tail local is not handed it — a silent wrong answer).  The port's rule
for the handover: the tail local goes to its bind's call and to every bind of it directly
before, unless that call's arguments read the local.
