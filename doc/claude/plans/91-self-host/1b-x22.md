# @PLN91 strand 1b — X22: a `match` the interpreter dispatches in one step

A child document of [1b-interpreter.md](1b-interpreter.md), for its friction row X22.  Status:
**step G (the guard fix) DESIGNED, not built; step T (the table jump) an outline.**

## The owner's scoping (2026-10-29)

- **It is an interpreter issue.**  rustc and gcc already turn a compare chain into a jump table,
  "though not always reliably"; the native generators are left as they are.  The table jump
  (step T) is the bytecode writer's alone.
- **The trouble is that a `match` arm can carry extra conditions** — a guard, a payload pattern
  — so the chain is not a plain list of equalities.  Measured first (below), that led to step
  G, which comes before T by the owner's call: **design the guard fix first.**

## What a guard does to the IR today

Each of the three chain builders in `src/parser/control.rs` lowers a guarded arm the same way:

```loft
match c {
  A if n > 5 => 1,   // if c == A { if n > 5 { 1 } else REST } else REST
  A | B => 2,        //   REST, the chain of every later arm, is built ONCE and placed TWICE
  D => 3,
  E if n < 0 => 4,   //   a second guard copies its own REST inside both copies
  _ => 5,
}
```

A payload test is the same shape (`P { x: 1 }` lowers to `tag == P` then a `field_sub` condition
inside the arm).  Measured on an eight-arm plain-enum match, by the number of guarded arms
(`introspect`, the IR's `OpEqInt` count and the function's bytecode ops):

| guarded arms | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| subject tests in the IR | 8 | 15 | 27 | 47 | 79 | 127 | 191 |
| bytecode ops | 62 | 114 | 204 | 356 | 604 | 988 | 1532 |

About ×1.6 per guard: exponential, on every backend's code size and compile time.  The
builders' own comment knows the copy (`chain_pattern_arms`: "The `<rest>` appears twice, as it
does in the enum arm chain this mirrors; only an arm that actually carries a guard pays for
it") — what it did not count is that the copies compound.

## Step G — a guard is a condition on its own arm

### The invariant

**Every arm's code — its bindings, its guard, its body — is emitted once, and a failed guard
continues with the next arm (`@FR-P-Guard`: "cond false ⟹ the arm ⇓ Fail … selection moves to
the NEXT arm").**  The builders' standing constraints stay: the bindings run once, only inside
the branch their pattern selected, and before the guard reads them (a slice arm's `..name`
materialisation and a PEG cursor advance cannot run twice).

### The shape

```loft
A if n > 5 => 1,        // today:    if c == A { if n > 5 { 1 } else REST } else REST
                        // proposed: if (if c == A { n > 5 } else false) { 1 } else REST
P { x } if x > 3 => x,  // today:    if tag == P { _mv_x = s.x; if _mv_x > 3 { _mv_x } else REST }
                        //           else REST
                        // proposed: if (if tag == P { _mv_x = s.x; _mv_x > 3 } else false)
                        //             { _mv_x } else REST
```

The condition is `cmp && { bindings; guard }`, written as the IR's own short circuit
(`If(cmp, Block{…}:boolean, false)`), so the bindings and the guard still run only after the
pattern test holds, in the same order as today; `REST` is placed once.  An unguarded arm and a
guarded WILDCARD (`v_if(guard, body, REST)`, no copy today) are unchanged.

**One home.**  The three builders — the enum chain (`parse_match`, the arm loop near `guarded
arms nest the guard inside the pattern branch`), the scalar chain (`build_scalar_chain`'s
range and equality arms) and `chain_pattern_arms` — each call one function, `guarded_arm(cmp,
bindings, guard, body, rest, tp) -> Value`, that writes the shape above.  The three copies of
today's shape go with it.

### What can break, and the probe for each (before building)

The move changes WHERE the bindings are first written: inside the condition, no longer inside
the arm's then-block.  Each claim below is probed on both backends with `LOFT_STRICT_STORES=1`
before the change is trusted, with the builder behind a switch (`LOFT_NO_GUARD_ARM=1` keeps
today's shape) so every cell runs both ways:

- **G1 — an owned binding is not freed before the body reads it.**  The scope pass frees a
  variable at the exit of the scope it is first written in; `scan_if` pre-initialises a text,
  reference or vector variable first assigned in a BRANCH (`find_first_ref_vars`), but the
  bindings now sit in a CONDITION.  Cells: a text payload read in the body (`Word { s } if
  len(s) > 1 => s`), a `..rest` slice binding read in the body, a record payload, each in a
  loop.  If G1 fails, the builder emits the bindings' pre-inits before the `if` itself — the
  shape `scan_if` already writes — rather than asking the scope pass to look into conditions.
- **G2 — a scalar binding keeps its slot from the condition into the body**, against a body
  local that could reuse a slot freed at the condition block's end (`Block` slots are
  per-scope).  Cell: `P { x } if x > 3 => { y = x * 2; x + y }`.
- **G3 — a failed guard leaves nothing observable** (`@FR-P-Atomic`).  Today's shape already
  runs REST after the bindings ran, so a PEG cursor advance or a materialised `..rest` is
  visible to the later arms there too; the cell measures today's answer FIRST, and a deviation
  found there is a separate defect, fixed on its own.
- **G4 — every arm order and every guard count answers as before**: the 8-arm table above, as
  a matrix of guard placements × which arm the subject selects × whether each guard holds,
  values hand-computed, on both backends.
- **G5 — the IR is linear in the guards**: the table above re-measured.  Expected: 8 subject
  tests at every guard count (each arm's test once), and the bytecode growing by one guard's
  ops per guarded arm.

### How it is measured and guarded

- The matrix (G4) graduates to the language suite under `@FR-P-Guard`, both backends.
- The IR size (G5) becomes a guard of its own: a test that lowers the eight-arm match with six
  guards and asserts the subject-test count stays linear, falsified against today's tree
  (`make falsify`), where it reads 191.
- `make suite` (the `matching` chapter, then all), the front-end allocation pins (the stdlib
  parse should DROP: every guarded `match` in `default/` stops copying), and the S1 tests'
  time under `--interpret`.

## Step T — the table jump (outline, designed after G lands)

In the bytecode writer only: a chain whose tests compare one pure subject (a variable, a plain
enum's number, a variant tag read) with literals or literal ranges gets a table indexed by the
subject's value, holding the first arm whose test can hold for that value.  Execution enters
the chain there; every arm's own test, guard and body still run as written, so the only tests
skipped are comparisons that are false for this value — which never skips or reorders a guard,
since a guard is evaluated only after its arm's test passes.  An arm whose test the writer
cannot classify ends the table.  With G landed, the chain is flat, so one table serves the
whole match.
