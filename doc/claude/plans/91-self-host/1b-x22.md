# @PLN91 strand 1b — X22: a `match` the interpreter dispatches in one step

A child document of [1b-interpreter.md](1b-interpreter.md), for its friction row X22.  Status:
**step G (the guard fix) BUILT — `D-match-26` closed; G2 (the tag read once) DESIGNED, with
one decision open for the owner; T (the bytecode writer's representation choice) an outline.**

## The owner's scoping (2026-10-29)

- **It is an interpreter issue.**  rustc and gcc already turn a compare chain into a jump table,
  "though not always reliably"; the native generators are left as they are.  The table jump
  (step T) is the bytecode writer's alone.
- **The trouble is that a `match` arm can carry extra conditions** — a guard, a payload pattern
  — so the chain is not a plain list of equalities.  Measured first (below), that led to step
  G, which comes before T by the owner's call: **design the guard fix first.**

**The rules.**  Step G closes `D-match-26` against `(M-Once)` (`formal/matching.md`: a match is
lowered once per arm; a failed guard reaches the next arm through control flow), and keeps
`(P-Guard)` and `(P-Atomic)` as they stand.  The order G then T is `(Perf-Order)`
(`formal/performance.md`): the IR first, an interpreter operator built for speed after it.

## What a guard does to the IR today

Each of the three chain builders in `src/parser/control.rs` lowers a guarded arm the same way:

```loft
match c {
  A if n > 5 => 1,   // if c == A { if n > 5 { 1 } else REST } else REST
  A | B => 2,        //   REST, the chain of every later arm, is built ONCE and placed TWICE
  D => 3,
  E if n < 0 => 4,   //   a second guard copies its own REST inside both copies
  _ => 5,
}
```

A payload test is the same shape (`P { x: 1 }` lowers to `tag == P` then a `field_sub` condition
inside the arm).  Measured on an eight-arm plain-enum match, by the number of guarded arms
(`introspect`, the IR's `OpEqInt` count and the function's bytecode ops):

| guarded arms | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| subject tests in the IR | 8 | 15 | 27 | 47 | 79 | 127 | 191 |
| bytecode ops | 62 | 114 | 204 | 356 | 604 | 988 | 1532 |

About ×1.6 per guard: exponential, on every backend's code size and compile time.  The
builders' own comment knows the copy (`chain_pattern_arms`: "The `<rest>` appears twice, as it
does in the enum arm chain this mirrors; only an arm that actually carries a guard pays for
it") — what it did not count is that the copies compound.

## Against what compilers do (owner's question, 2026-10-29)

**No production match compiler copies the arms after a guard.**  rustc lowers a `match` to MIR
"candidates", and a failed guard is an edge to the next candidate's test block; OCaml's matcher
shares code through exits (Le Fessant & Maranget's backtracking automata) so that it does not
duplicate.  Both use labelled blocks; the IR has none, and `if (cmp && { bindings; guard })
body else rest` is how an expression IR draws the same graph.  The flat chain it leaves is also
the shape LLVM's SimplifyCFG and gcc's if-to-switch pass recognise, so step G is right for every
backend, not only the interpreter.

**Whether a match becomes a table is a COST decision, made per match.**  A compiler chooses a
jump table, a bit test, a balanced binary search or a compare chain by the number of cases and
their density, and removes tables again: for a small or sparse switch (a few predicted branches
beat one indirect jump), for a constant-valued one (a lookup table of values, no jump), under
`-mretpoline` / `-fno-jump-tables` (an indirect branch is a speculation risk), and under a
profile (the hot case peeled before the table).  What carries over to the bytecode:

- The branch-prediction and speculation reasons do NOT: a bytecode table only sets the next
  `pc`, and the host dispatches each bytecode op once whatever the table holds.
- The interpreter's cost model is OPS DISPATCHED.  An enum arm's test is six ops today
  (`VarRef, GetEnum, ConvIntFromEnum, ConstInt, EqInt, GotoFalseWord`; an integer literal one
  fused `CmpIntVCJump`), so a 66-arm chain dispatches about 400 ops before its last arm, where a
  table costs two or three.  The break-even is measured here, never borrowed from LLVM.
- Sparseness and tiny matches DO carry over: a sparse match keeps its chain or takes a binary
  search, and a two- or three-arm match may not pay for the table op itself.  A match whose arms
  all yield constants could later take a value table; that is not part of this plan.

## Step G — a guard is a condition on its own arm

### The invariant

**`(M-Once)`: every arm's code — its bindings, its guard, its body — is emitted once, and a
failed guard continues with the next arm (`(P-Guard)`: "cond false ⟹ the arm ⇓ Fail …
selection moves to the NEXT arm").**  The builders' standing constraints stay: the bindings run once, only inside
the branch their pattern selected, and before the guard reads them (a slice arm's `..name`
materialisation and a PEG cursor advance cannot run twice).

### The shape

```loft
A if n > 5 => 1,        // today:    if c == A { if n > 5 { 1 } else REST } else REST
                        // proposed: if (if c == A { n > 5 } else false) { 1 } else REST
P { x } if x > 3 => x,  // today:    if tag == P { _mv_x = s.x; if _mv_x > 3 { _mv_x } else REST }
                        //           else REST
                        // proposed: if (if tag == P { _mv_x = s.x; _mv_x > 3 } else false)
                        //             { _mv_x } else REST
```

The condition is `cmp && { bindings; guard }`, written as the IR's own short circuit
(`If(cmp, Block{…}:boolean, false)`), so the bindings and the guard still run only after the
pattern test holds, in the same order as today; `REST` is placed once.  An unguarded arm and a
guarded WILDCARD (`v_if(guard, body, REST)`, no copy today) are unchanged.

**One home.**  The three builders — the enum chain (`parse_match`, the arm loop near `guarded
arms nest the guard inside the pattern branch`), the scalar chain (`build_scalar_chain`'s
range and equality arms) and `chain_pattern_arms` — each call one function, `guarded_arm(cmp,
bindings, guard, body, rest, tp) -> Value`, that writes the shape above.  The three copies of
today's shape go with it.

### What can break, and the probe for each (before building)

The move changes WHERE the bindings are first written: inside the condition, no longer inside
the arm's then-block.  Each claim below is probed on both backends with `LOFT_STRICT_STORES=1`
before the change is trusted, with the builder behind a switch (`LOFT_NO_GUARD_ARM=1` keeps
today's shape) so every cell runs both ways:

- **G1 — an owned binding is not freed before the body reads it.**  The scope pass frees a
  variable at the exit of the scope it is first written in; `scan_if` pre-initialises a text,
  reference or vector variable first assigned in a BRANCH (`find_first_ref_vars`), but the
  bindings now sit in a CONDITION.  Cells: a text payload read in the body (`Word { s } if
  len(s) > 1 => s`), a `..rest` slice binding read in the body, a record payload, each in a
  loop.  If G1 fails, the builder emits the bindings' pre-inits before the `if` itself — the
  shape `scan_if` already writes — rather than asking the scope pass to look into conditions.
- **G2 — a scalar binding keeps its slot from the condition into the body**, against a body
  local that could reuse a slot freed at the condition block's end (`Block` slots are
  per-scope).  Cell: `P { x } if x > 3 => { y = x * 2; x + y }`.
- **G3 — a failed guard leaves nothing observable** (`@FR-P-Atomic`).  Today's shape already
  runs REST after the bindings ran.  Measured on today's tree, both backends, strict stores: a
  binding that shadows an outer local and fails its guard leaves the later arm reading the
  outer value, and a `..rest` materialised by a failed guarded arm leaves the next arm binding
  its own (`5 2 len 3`).  The change must keep exactly that answer; a cursor match is added to
  the cells when step G is built.
- **G4 — every arm order and every guard count answers as before**: the 8-arm table above, as
  a matrix of guard placements × which arm the subject selects × whether each guard holds,
  values hand-computed, on both backends.
- **G5 — the IR is linear in the guards**: the table above re-measured.  Expected: 8 subject
  tests at every guard count (each arm's test once), and the bytecode growing by one guard's
  ops per guarded arm.

### How it is measured and guarded

- The matrix (G4) graduates to the language suite under `@FR-P-Guard`, both backends.
- The IR size (G5) becomes the `(M-Once)` guard: a test that lowers the eight-arm match with six
  guards and asserts the subject-test count stays linear, falsified against today's tree
  (`make falsify`), where it reads 191.  The four sites citing `@FR-D-match-26` in
  `src/parser/control.rs` become one `guarded_arm` citing `@FR-M-Once`, and the deviation
  moves to the history companion as CLOSED.
- `make suite` (the `matching` chapter, then all), the front-end allocation pins, and the S1
  tests' time under `--interpret`.

### Built

`parser::control::guarded_arm` writes the shape; the enum chain, `build_scalar_chain`'s range and
equality arms and `chain_pattern_arms` call it (`keys::guard_arm_enabled`, `LOFT_NO_GUARD_ARM=1`
for the copying shape).  Measured:

- **G1–G4:** 178 cells (the hand-computed ones, the eight-arm matrix over 0–6 guards × every
  subject × three guard inputs, the `(P-Atomic)` pair) equal on both backends, in both switch
  states, under `LOFT_STRICT_STORES=1`.  The bindings first written inside a condition needed
  nothing new: no binding was released before its body read it.
- **G5:** 8 subject tests at every guard count (191 at six before); the bytecode 62 → 86 ops
  over 0–6 guards (62 → 1532 before).
- `make suite`, both backends: all cells, the new `rules/matching/M-Once/` file included.
- Byte-identity (`scripts/introspect_diff.sh`, the switch against the fold, over the corpus and
  the language suite): 27 of 2916 files lower differently, and every one holds a guarded arm or
  a field sub-pattern (`Circle { radius: 4 }`, `Wrap { inner: Leaf { items } }`), which the
  parser lowers as an arm condition through the same builder; the other 2889 are identical.
- The front-end allocation pins do not move: the standard library holds no guarded arm, so
  the prediction above that its parse would drop was wrong.

**Design → code.**  Transcribed directly: one function, four call sites, the switch.  The
probes found nothing to bend around.  One side finding, filed rather than fixed here
(loft#2225, the native generator): a value `if` of text whose arm calls a function with a
struct-enum literal argument does not compile on `--native`.

## Step G2 — the subject's tag is read once: DESIGNED

### What an arm's test costs today (measured)

The bytecode writer already fuses `if <integer variable> == <literal>` into ONE op,
`CmpIntVCJump`: an integer `match` costs one op per arm.  An enum `match` does not get it,
because every arm tests `OpEqInt(OpConvIntFromEnum(<subject>), lit)` and the conversion stands
between the variable and the compare:

| subject | ops per arm test |
|---|---|
| an integer local (`match i { 0 => …`) | 1 — `CmpIntVCJump` |
| a plain enum (`match c { A => …`, `match o.code { … }`) | 5 — `VarEnum, ConvIntFromEnum, ConstInt, EqInt, GotoFalseWord` |
| a struct enum (`match s { P { x } => …`) | 6 — `VarRef, GetEnum, ConvIntFromEnum, ConstInt, EqInt, GotoFalseWord` |

So G2 needs no new operator: the match reads the tag ONCE into an integer temp,
`_match_tag = OpConvIntFromEnum(<subject or OpGetEnum(s, 0)>)`, and every arm tests
`OpEqInt(_match_tag, lit)`, which the existing fusion turns into one op.  The interpreter's
66-arm run loop then walks 66 ops to its last arm instead of about 330.  It is IR work, so
`(Perf-Order)` takes it before any new operator, and native compilers meet a chain of
equality tests on one local.

### The edge that decides it — a guard that writes the subject

```loft
fn flip(s: &S) -> boolean { s = Q { y: 7 }; false }

match s {                 // s is a P { x: 3 }
  P { x } if flip(s) => x,   // the guard rebinds s to a Q, then fails
  Q { y } => y,              // today: the tag is read again, s is a Q now → 7 (both backends)
  P { x } => x,              // tag read once: P still → this arm, reading x out of the Q record
  _ => 0,
}
```

Reading the tag once tests the later arms against the OLD tag while their payload bindings read
the CURRENT record: a Q's field read at a P's offset, or a record the rebind freed.  So the
tag-once lowering is sound only where nothing between two arm tests can write the subject.
Today's re-reading is consistent (tag and payload both current) but is not what `(M-Match)`
states — the arms are matched against `v`, the scrutinee's value at the start.  rustc refuses
the shape: a guard may not mutably borrow the scrutinee (E0510).

**This is a decision for the owner** (a change to a shipped answer, or a refusal of a shipped
program).  The options, each with what it costs:

1. **Refuse a guard that can write the subject** — rustc's answer, and the default the formal
   README names when a shape's admission is unclear.  Then `(M-Match)` holds as written and
   G2 applies to every match.  A program spelled this way stops compiling; how many exist is
   measured over the corpus before the refusal ships.
2. **State the re-read in `(M-Match)`** — each arm is tested against the subject as it is when
   that arm is reached.  Today's answers stand, and G2 applies only where no guard can write
   the subject.
3. **Read once and copy the payload source too** — the arms test and bind from the value at
   the start.  It needs the subject held apart from a rebind, which a heap enum is not.

**Recommended: 1**, for the reasons rustc has: the shape has no reading in which the tag and
the payload agree without either a refusal or a copy, and the programs it refuses are ones
whose meaning already depends on which lowering ran.

### What G2 builds before the answer, and after it

- **Before:** the tag-once lowering only for a match whose guards cannot write the subject —
  none of its guards (and no field sub-pattern) contains an assignment to the subject, a call
  that takes the subject by `&`, or a call whose argument can reach the subject's store.  A
  match with no guard at all (the run loop) always qualifies.  `LOFT_NO_TAG_ONCE=1` keeps
  today's lowering.
- **After option 1:** the refusal (with its `M-Match` clause and a diagnostic naming the guard),
  and the gate goes: G2 applies everywhere.

### Probes (before building), each on both backends, strict stores

- **P1** — the table above re-measured after the change: 1 op per arm test for a plain enum,
  a field (`o.code`) and a struct enum.
- **P2** — the edge: the program above answers 7 on both backends with G2 built (the gate
  keeps it on the re-reading path), and a match differing only in a pure guard takes G2.
- **P3** — a nullable subject: an absent `E?` reads tag 0 once and matches no variant arm,
  falling to `_` (`(M-Unit)`'s absence clause).
- **P4** — the S1 tests and the census, timed under `--interpret`, before and after.
- **P5** — byte-identity: a match the gate declines lowers exactly as today
  (`scripts/introspect_diff.sh`, the switch against the change).

## Step T — the bytecode writer chooses the representation (outline, after G2)

In the bytecode writer only, and as a COST decision: a chain whose tests compare one pure
subject with literals or literal ranges takes a table when its arms are dense and at least a
threshold in number, a binary search when they are many but sparse, and stays a chain
otherwise.  The thresholds are measured on this interpreter — the S1 tests, the census, and a
synthetic match by arm count and density — and recorded beside the rule (an `(R-…)` entry in
`formal/rewrites.md`, interpreter phase, with its `LOFT_NO_…` switch).

A table holds, per subject value, the first arm whose test can hold for it.  Execution enters
the chain there; every arm's own test, guard and body still run as written, so the only tests
skipped are comparisons false for this value — which never skips or reorders a guard, since a
guard runs only after its arm's test passes.  An arm whose test the writer cannot classify
ends the table.  The native generators are untouched: their compilers keep or drop a table by
their own cost model, from G's flat chain.
