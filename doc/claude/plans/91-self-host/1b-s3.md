# @PLN91 strand 1b — phase S3, the store: paper design

A child document of [1b-interpreter.md](1b-interpreter.md).  Status: **the first two slices are
BUILT** — records (every field width, texts, embedded records, copies) and vectors — on all
three backends, with ownership decided at run time (§ Ownership at run time, BUILT); the third, struct
enums, and the fourth, hashes with their walks, are built (§ The third slice, § The fourth
slice and its continuation).  The direction is the owner's
(plan § S3): the running program's records, vectors and texts live in the C runtime's own
stores, reached through `selfhost/crt`.

## Why S3 is next

The census (1 018 programs) passes 27 and answers none wrong; of the 987 it refuses, 663 stop at
a record (`TyReference`), 118 at a vector, 53 at a struct enum and 33 at a hash.  Every one of
them is a value the store holds.

## The invariant

**A value the interpreted program keeps in a store is a record of the C runtime's stores, laid
out by the image's type table, and only the C runtime's own routines read, write, claim, copy
or free it.**

The interpreter's loft code never computes an address, a size or a field offset of its own.  An
operator that names a field passes the field's byte offset from the IR (`OpGetInt(p, 8)`)
unchanged.  So the interpreter cannot disagree with a `--native-c` program about where a
field is or when a record is freed.

Where the invariant is asserted, and so where it can break:

1. **One `crt` routine per store operator**, each calling the runtime's routine of that
   operator: `OpGetInt` → `loft_get_int`, `OpSetText` → `loft_set_text`, `OpDatabase` →
   `loft_database_typed`, `OpFreeRef` → `loft_free_ref`, `OpCopyRecord` → `loft_copy_record`.
   The runtime already defines every one of these (`src/c/loft_rt.h`).
2. **One representation of a reference in the interpreter** (question 1).
3. **One type table** handed to the runtime (question 2), derived in loft.

## The stores are the shim's own

`loft_crt.h` includes the runtime's first three headers.  Their globals are `static`, so the
`crt` shim has its own copy of the runtime, and with it its own stores:

- Under `--interpret`, the shim is loaded as a library, and its stores are the only C stores in
  the process.
- Under `--native-c`, the interpreter itself is a C program with its own stores.  The shim's
  copy sits beside them, and the two never meet.

The interpreted program's data therefore never mixes with the interpreter's own: a
`loft_free_ref` in the program cannot release an interpreter record.  Probe P4 checks this
before anything is built on it.

## Question 1 — how a reference crosses a `#c` call — DECIDED (owner): its three parts

A reference is `{store_nr: u16, rec: u32, pos: u32}` (`loft_rt.h:1045`), 80 bits, and a `#c`
argument is a scalar of at most 64.  `pos` can exceed 16 bits: a reference to a vector element
is the vector's record plus `8 + i × size`.

**A reference is its three parts, as three integers.**  It is a new kind, `KRef`, held as three
adjacent slots on the integer stack, and every `crt` store routine takes `(store, rec, pos)`.
The parts map one to one onto `loft_ref`, so neither side packs or masks anything.  The null
tests are read in loft, as the C generator writes them: `OpRefIsNull` is `store == 65535` (the
sentinel `loft_ref_null()` writes), `OpConvBoolFromRef` is `rec != 0`.  `#c` takes up to 32 arguments (`c_call.rs`); the
widest first-slice routine, `loft_copy_record`, takes eight.

```loft
// the IR of `p.x += d`:  OpSetInt(p, 0, OpAdd(OpGetInt(p, 0), d))
crt::set_int(p_store, p_rec, p_pos, 0, crt::get_int(p_store, p_rec, p_pos, 0) + d)
```

Declined:
- **Two integers** (`store_nr << 32 | rec`, `pos`).  One argument fewer, but packing and masking
  on both sides of every crossing, and a mask written wrong gives a reference that is quietly
  wrong.
- **A handle table in the shim**, which keeps a second record of every live reference.
- **One 64-bit integer**, which limits `pos` to 16 bits and breaks silently past byte 65 535.

## Question 2 — the type table — DECIDED (owner): loft derives it

`loft_copy_record`, the free of a record that owns texts or vectors, and every keyed collection
read a table of type descriptors (`loft_tdesc`: kind, size, fields with their offsets, element
type, variants, keys, `owns_heap`, `linked`).  The C runtime only READS this table; nothing in
it derives a row.  A `--native-c` program has the table compiled in, written by the C
generator's `copy_table` (`src/c/mod.rs`) from the program's store schema.  The interpreter has
the same schema in the image (`Bundle.types`), but no table.

```loft
struct Point { x: integer, y: integer, name: text }
q = p;      // OpCopyRecord: the runtime copies `name`'s text because the table says field 2 is a
            // text at byte 16 and the type owns heap; with `owns_heap` wrong, q.name and p.name
            // share one claim, and freeing p leaves q reading freed text
```

**The interpreter derives the table in loft from `Bundle.types`**, because the goal is to drop
the rustc dependency (the owner's ruling: depend on the C runtime, never on loft's rustc side).
Most of a row is stored in the schema: the kind, the size, the element type, each field's byte
offset and type, and `linked`.  Four values are computed, and the loft code ports each one from
its Rust home:

| value | Rust home |
|---|---|
| `owns_heap` | `Stores::type_owns_heap` (`src/database`) |
| a field's `view` and `group` | `group_owner`, `Stores::nullable_some_variant` (`src/c/mod.rs`, `src/database`) |
| a keyed collection's key parts | `keys_of` (`src/c/mod.rs`) |

The port is the one move of logic a self-hosted toolchain needs anyway (strand 1a writes the
image itself), not a second copy kept for good.  **While the Rust generator exists, a guard keeps
the two equal**: for every program of the corpus, the loft-built table and the C generator's
table are compared row by row, so a port error shows as a named row and value, never as a
quietly wrong copy.  The guard retires with the Rust generator.

**The only new C is marshalling.**  Loft cannot produce C pointers, so one shim function,
`loft_crt_load_types`, copies flat integer rows into `loft_tdesc`, `loft_fld` and `loft_key`
structs and links their pointers.  It decides nothing about layout.

Declined:
- **The image carries the rows** (`copy_table` split, `--emit-image` stores them).  This puts one
  more output only Rust produces into the image, which would have to be ported later anyway.
- **C functions that compute the values**, which would port the same Rust logic into C instead
  of loft and break the `crt` rule (only routines the runtime already defines).

## The first slice — records of scalars and texts

What the census's smallest record programs emit (`introspect` of a three-field struct, a
constructor, a mutating call and a copy):

| operator | runtime routine | note |
|---|---|---|
| `OpDatabase`, `OpDatabaseNP` | `loft_database_typed` | a fresh record of a type |
| `OpGetInt`, `OpSetInt` (and the `Int4`, byte and short widths) | `loft_get_int`, `loft_set_int`, `loft_get_int4`, … | the width is the operator's |
| `OpGetText`, `OpSetText` | `loft_get_text`, `loft_set_text` | a text is copied out into the interpreter's text stack |
| `OpCopyRecord` | `loft_copy_record` | reads the table of question 2 |
| `OpFreeRef`, `OpFreeRefIfDistinct` | `loft_free_ref` | |
| `OpRefIsNull`, `OpConvBoolFromRef` | none | `store == 65535` and `rec != 0`, read in loft |

Vectors, struct enums, hashes and the other keyed collections are later slices, each using the
same three assertion sites, and each sized by the census once the first slice lands.

## The first slice — the build

**What a bind means is the generator's decision, not an operator.**  `q = p` reaches the IR as
`Set(q, Var(p))`; the bytecode writer makes it `OpBindOrCopy`, the C generator
`loft_bind_copy` (`set_stmt`, `src/c/body.rs`).  The loft lowering follows `set_stmt`'s order
and carries the arms the image decides; every other arm is refused by name.

| `v = x`, `v` a record | what the slice does | C generator's arm |
|---|---|---|
| `x` is null | the null reference | `assign` |
| `x` a variable, same type (`copies_as`), `v` no overwritten view, first bind | `loft_bind_copy` | `whole_value_bind` |
| `x` a call of a loft function whose result declares no dependency (`return_adopts_fresh_store`), first bind | adopted | none of the copy arms fires |
| `x` a call of an operator or a native | assigned | `assign` |
| a rebind, a `&` record parameter, any other call | **refused** | `displacing_rebind`, `link_rebind`, `join_stmt`, `call_copy` |

The call arm's test is sound for the copy arms (`call_copy` returns `None` exactly then), but
not provably for `join_stmt`, which asks `ownership_of`'s interprocedural summary of the
callee.  The census's leak check (below) is the falsifier; porting the summary is the O track's
([ownership.md](ownership.md)), so the slice does not.

**The interpreter's side.**
- `KRef`: a reference is three adjacent slots on the integer stack, a variable three slots of
  the frame, a parameter three of `params_int`.  `Load`, `Store`, `Pop`, `PushNull` and `Ret`
  of `KRef` move three.
- One op per row of the operator table above, each calling its `crt` routine.  An operator
  that writes the VARIABLE (`OpDatabase`, `OpFreeRef` of a variable, `OpFreeRefIfDistinct`,
  the bind copy) hands `crt` the variable's three parts and writes back what the runtime left:
  `loft_database` clears the store a variable already names, `loft_free_var` resets only the
  store part.  So the shim's `database` takes the reference in as well as out.
- The type table is loaded on the first op that reads it (a copy), from `types::row` over
  every type of the image.
- **The leak check:** `run` answers how many of the shim's stores are live after the entry
  returns; for a program whose records the IR frees, zero.

## Where the slice stands

**Census: 1 026 programs, 60 pass, 0 leak, 0 wrong, 0 crash, and no passing program has a store
swept** (27 before S3): wherever a program runs, the IR's frees and the owner table agree.  The
slice carries every field width (`crt::get_w`/`set_w`, `get_float`/`set_float`, a plain enum's
byte), `OpGetField`, `OpCopyRecord` (with `swap_safe` ported to `types.loft`), `OpClear` (its
claim walk; the pool reset is a switchable optimisation), the reference writes `OpPutRef` and
`OpInitRefSentinel`, and binds of every kind (§ Ownership at run time).  Two wrong answers the
census found on the way were lowering defects, fixed with a guard each: a bind read its value
without stripping the source span around it, and a value block took its last operator as its
value where frees follow it.  Refused next, by programs: vectors 451, struct enums 88, hashes
58, `OpNewRecord` 35, tuples 32, function values 32, a `&` record (`OpCreateStack` of a
record) 31.

**A known cost:** a caller that reuses its return buffer across a loop (`OpClear` of `__ref_N`,
then the call fills it) has a store its variable owns, so the bind copies where the C
generator views the buffer: one copy per pass, values the same.

## Ownership at run time — DECIDED (owner, 2026-10-28)

**Ruling:** a record bound from a call is decided at run time by (O-Move), *integrated with the
lifetimes so there is no room for disagreement*.  So the bind and every free read ONE fact.

**The invariant — `(O-Owner)` held at run time:** the interpreter keeps an owner table, one entry
per store of the C runtime: the variable slot that owns it, or the frame holding it in flight (a
returned value not bound yet), or nobody.  Every operator that creates, binds, frees or returns
a record reads and updates that entry, and no store is released except through it.

| event | what the table does |
|---|---|
| `OpDatabase(v)` | `v` owns its store: made again in place.  Otherwise a fresh store, owned by `v` (never a clear of a store `v` only views) |
| `v = x`, `x`'s store held in flight by this frame, or by nobody | ADOPT: `v` owns it |
| `v = x` copying (a record variable, a projection `element_copy` copies, a loft call whose result lives in a store someone owns) | COPY into `v`'s own store (refilled in place when `v` owns one) |
| `v = x` otherwise (a view) | `v` names the store, owns nothing |
| any bind | a store `v` owned and no longer names is freed (`displacing_rebind`) |
| `OpFreeRef(v)`, `OpFreeRefIfDistinct(v, w)` | freed only when THIS FRAME owns it — through any of its variables, since a vector's field variable names its wrapper's store — never a store a caller owns; `v` is reset as the runtime resets it |
| `OpCopyRecord` that frees its source | the source's entry goes with it |
| `Ret` | the returned store, if this frame owned it, is held in flight by the caller; every other store this frame owns or holds is freed (the SWEEP) |

**What this settles.**  A call bind needs no analysis of the callee: a record minted by the
call arrives in flight and is adopted; one that lives in a store somebody owns (an argument, a
field of one) is copied, which is (O-Move)'s borrow clause.  The IR's frees cannot disagree
with that choice, because a free acts only on what the table says the variable owns; and a free
the IR does not place for a store the interpreter owns is the sweep's.  Rebinds and parameters
need no refusal for the same reason.

```loft
c = keep(src);    // the result is src's store, owned by src: copied, c owns the copy
f = file("x");    // file() minted it in its own frame; returned in flight: f adopts it
p = make(1, 2);  p = make(3, 4);   // the second bind frees the first store p owned
```

**The leak check stays a falsifier:** `stores_left` counts the stores live after the run, and
`swept` counts what the sweep released — the frees the IR did not place.  A swept store is no
fault (the table owned it), but the census reports it, as the measure of where the static
lifetimes and the run-time ones differ.

**What a later slice must add to the table:** an operator that stores a reference INTO a record
(`OpSetDbRef`, a vector push of a record) moves ownership from a variable to the container; it
is refused until it does.

## The second slice — vectors: BUILT

**Census after it: 1 026 programs, 117 pass, 0 leak, 0 wrong, 0 crash, none swept** (60 after
the first slice).  Refused next, by programs: struct enums 127, hashes 61, function values 51,
`n_write_bytes` 51, a `&` record or vector (`OpCreateStack`) 49, `OpFormatDatabase` 46,
`OpAppendVector` 46, tuples 41, `OpDistinctStore` 27, iterators 22, an owned vector whose
element is a narrow integer 16 (`element_type` resolves base types and records only),
`OpAppendCopy` 14.  The measurement and the design below are as built; one rule moved on the
way: a free acts on what the FRAME owns, because the IR frees a minted vector through the field
variable that views its wrapper (§ Ownership at run time).

**Measured first** (`TyVector` lowered as a reference, nothing else changed): the vector
programs then stop at the bind of a vector variable (`v` 96, `empty` 47, `_vec_1` 29, …), at
`OpNewRecord`/`OpFinishRecord` 38, the pushes (`OpPushInt` 27, `OpPushFloat` 9), the element
reads (`OpGetVector` 17, `OpGetVectorNullable` 13) and `OpClearVector` 5.

**What a vector is, in the IR.**  A vector variable is a reference to the FIELD that holds the
vector inside a wrapper record: `OpDatabase(__vdb_1, main_vector<P>)` mints the store, and
`ps = OpGetField(__vdb_1, 0, vector<P>)` names its field.  An element is a reference into the
same store (`OpGetVector(ps, size, i)`).  So a vector is a `KRef`, and the owner table already
says who owns it: the wrapper variable owns the store, `ps` and every element are views.

**Binds.**  The C generator has no copy arm for a vector (`heap_def_nr` names records only):
a vector bind is a view, PLAIN, with one exception — `v = null` for a vector that owns its
store (no dependency, not skip-free, not an inline ref; `owned_vector_null`) mints a wrapper of
`main_vector<T>` into `v` itself, which the table records as `v`'s.  The `main_vector<T>` type
is found by its name in the image's schema.  A record element bound to an owning variable
copies (`element_copy`): the projection walk follows `OpGetField`, `OpGetVector`,
`OpVectorRef` and `OpGetRecord` (not the nullable reads) to a variable, as
`projection_walk` does.

**Operators, each to its runtime routine** (`crt`, marshalling only):

| operator | runtime routine |
|---|---|
| `OpLengthVector(v)` | `loft_vec_len` |
| `OpGetVector`, `OpGetVectorNullable(v, size, i)` | `loft_vec_get` |
| `OpPreAllocVector(v, n, size)` | `loft_vec_prealloc` |
| `OpPushInt`, `OpPushInt4`, `OpPushFloat`, `OpPushSingle`, `OpPushCharacter`, `OpPushByte`, `OpPushEnum`, `OpPushBoolean` | `loft_vec_push_*` |
| `OpNewRecord(v, tp, 65535)` on a plain vector | `loft_vec_append`, then `loft_fill` with the element type's default image |
| `OpFinishRecord(v, e, tp, 65535)` | `loft_vec_finish` |
| `OpClearVector(v)` | `loft_vec_clear_release` (reads the type table) |

A keyed collection's `OpNewRecord` (a field `fld` other than 65535, or a keyed parent) is the
hash slice's, refused here.

**The default image is derived in loft**, the third value after the type table and
`swap_safe`: `types::default_image(b, tp)`, a port of `Stores::set_default_value`'s walk
(`src/database/structures.rs`, `Absent::Prefill`): an 8-byte integer's null, a float's NaN, a
boolean's 255, a type tag, a narrow integer's null by its part, an embedded record recursively,
zero for the rest.  The C generator always fills except where the literal writes every field
(`mint_complete`, an optimisation); the interpreter always fills.  **P6, the guard:** the
loft image of every element type equals the C generator's `loft_dflt{tp}` array, byte by byte,
as P5 compares the table.

**Cases** (`kernels/vectors.loft`, values by hand, value and leak and sweep asserted): an
integer vector built, pushed, summed and indexed; a vector of records built in a loop and
walked; a vector of texts; a vector field of a struct; a vector returned from a function and
one passed to one; an element bound and written through (a view) and one copied out; a cleared
vector refilled; an empty vector's length.

## The third slice — struct enums: BUILT 2026-10-29

**Census before it:** 127 programs stop at `a variable of a kind the interpreter does not carry
yet: TyEnum` — the most of any refusal.

**What a struct enum is, in the IR.**  It is a record already (`Type::heap_def_nr`:
`Reference(d)` and `Enum(d, true)` alike), so nothing new reaches the run loop:

```loft
enum Tok { Num { v: integer }, Word { s: text }, End }
t = Word { s: "w" };   // OpDatabase(__ref_1, <Word's type>); OpSetText(__ref_1, 4, "w");
                       // OpSetEnum(__ref_1, 0, 2) — a variant is minted at its own type, whose
                       // size is the enum's, its tag the byte at offset 0
match t { Word { s } => len(s), _ => 0 }
                       // if OpEqInt(OpConvIntFromEnum(OpGetEnum(t, 0)), 2) { OpGetText(t, 4) … }
c = ts[1];  d = c;     // binds as a record's: `copies_as` takes a variant into its enum
ts += [word(3)];       // OpCopyRecord(__lift_1, _elm_1, 0xC000 | <Tok's type>)
```

The tag test, the payload reads, a field holding an enum (`OpGetField`), a vector of them and
the copies are all operators S3 carries.  So the slice is:

1. **The kind** (`lower.loft: kind_of_type`): `TyEnum { is_ref: true }` is `KRef`, three
   integer slots, as `CType::Ref` makes it in C (`src/c/mod.rs`).
2. **The record it names** (`lower.loft: record_of`, `deps_of`): an `Enum(d, true)` names
   definition `d`, as `heap_def_nr` reads it, so a bind's copy arm (`whole_value_bind`,
   `call_copy`) and its type are the record's.
3. **The mint** (`lower.loft: mintable`): a variant's type (`PtEnumValue`) is minted as a
   struct's is.  The enum's own type is not minted by `OpDatabase` in any IR measured, and
   stays refused by name.
4. **The type table carries the variants** — the one gap that would answer WRONG, not refuse.
   `loft_copy_claims` and `loft_remove_claims` find a struct enum's payload through
   `d->variants[tag - 1]`.  `types::flat` drops the list `types::row` derives, so the runtime
   reads `n = 0` and copies the BYTES of a `Word` without its text claim: the copy names a claim
   of the source's store, and once the source is freed (`OpCopyRecord`'s flag 0x8000) it reads
   freed text.  The fix: a row carries its variant count after `linked` and the variants after
   its fields (`types::flat`); the shim's `loft_crt_load_types` reads them into `d->variants`
   and sets `d->n` to the count, as `copy_table` writes `{ LOFT_T_ENUM, size, 0, n, 0,
   loft_variants{tp} }`.  Marshalling only.
5. **The guard** (P5): `types::render` writes the variants, and `c_type_table`
   (`tests/selfhost.rs`) reads `loft_variants{tp}`, so a variant list that differs from the C
   generator's is a named row, not a silent copy.  Before the fix the guard compared no variant
   at all — the falsification is that it fails on a row with its list dropped.

**Ownership** needs nothing new: a struct enum's store is a record's store, so the owner table
decides its binds and frees as it does a struct's (§ Ownership at run time).

**Cases** (`kernels/enums.loft`, values by hand, value and leak and sweep asserted on every
entry): a variant built and matched, each arm; a unit variant; a variant returned from a
function and bound; `is`; a text payload copied (`c = a`) and the source freed, the copy read
after; a struct holding an enum field; a vector of struct enums built from literals, a call and
a unit variant, walked and matched (the `OpCopyRecord` of item 4); a rebind from a vector
element.

**Design → code (struct enums).**  Transcribed directly: the kind, the record a type names, the
mint and the type table's variant list are each a line or an arm.  One place took a detour: a
nullable type read through a self-call (`record_of(inner)`) drew `tail-call-not-jumped`,
because the argument is a fresh box-of-one; the arm reads `inner[0]` instead (X7's box-of-one,
again).  The slice found a loft defect on the way, fixed first (loft#2223): a view bound in a
later `match` arm was not materialised across a rebind of the subject, so the lowering's own
projection walk read a released store.

## The fourth slice — hashes: BUILT 2026-10-29

**Census before it:** 61 programs stop at `a variable of a kind … TyHash`.  This slice carries a
hash's build, lookup, length, copy and free; walking one (`for c in h`: `n_hash_sorted`'s
scratch, `OpIterate`/`OpStep` kind 4, `OpFreeScratch`) is the next step, sized by the census.

**What a hash is, in the IR and the runtime.**  A hash field is 4 bytes in its record (the
table's record number), its elements records of the SAME store, so the owner table needs nothing
new: the store's owner owns the hash and every element.  A hash local is minted at its null bind
AS the collection type (`keyed_null`, `src/c/body.rs`), as an owned vector is minted as its
`main_vector<T>`.

```loft
struct Count { name: text, n: integer }
h: hash<Count[name]> = [];   // h = null            → mint h's store as type `hash<Count[name]>`
h += [Count { name: "a", n: 1 }];
                             // OpNewRecord(h, <hash>, 65535)       → loft_hash_entry + loft_fill
                             // OpFinishRecord(h, elm, <hash>, 65535) → loft_hash_insert (an equal
                             //   key's element is replaced, @FR-Col-Insert)
c = h["a"];                  // OpGetRecord(h, <hash>, 1, "a")     → loft_h_find; a miss is rec 0
len(h)                       // t_4hash_len, a loft body: OpLengthHash → loft_hash_len
```

1. **The keys are already in the image** (`DbType.keys`: type, position, start), so the type
   table carries them unchanged — no port.  A row's `flat` form gains the key count and three
   numbers per key; the shim loads them into `d->keys`/`d->nk`, which `loft_copy_claims`,
   `loft_remove_claims` and the insert read.  P5 compares them with `loft_keys{tp}`.
2. **The routines read the keys from the loaded table**, so loft never hands a pointer: each
   `crt` hash routine takes the collection's type number and passes `T[tp].keys`.
3. **A lookup's key values go through a key STACK in the shim** — `crt::key_int`,
   `crt::key_float`, `crt::key_text` push one part, and `crt::hash_find(…, tp, n)` takes the top
   `n` and pops them.  A stack, not one builder, because a key can itself be a lookup
   (`h[g[k].name]`): the inner find pops its parts before the outer pushes its own.  The value
   is converted by the key's `type_nr` (`key_value`, `src/c/body/keyed.rs`): 3 single, 4 float,
   6 text, the rest an integer.  The general `loft_h_find`, not the typed entries
   (`@FR-R-TypedKeyed` is an optimisation, values unchanged).
4. **A hash local's type** is found by the name the schema gives it (`Stores::hash`):
   `hash<{content}[{key},…]>`, from the IR's `TyHash { n, names }`.  `-1` refuses by name.
5. **`OpNewRecord`/`OpFinishRecord`** extend the vector arm's `record_collection`: the
   collection type is the parent's (field 65535) or the field's; a vector keeps its arm, a hash
   takes `hash_entry`/`hash_insert`, any other keyed kind or a linked group stays refused.

**Code points:** `lower.loft` (`kind_of_type`, `bind`'s keyed null arm, `mintable`, the
`OpNewRecord` arm, `OpGetRecord`, `OpLengthHash`), `run.loft` (the ops `HashNew`, `HashInsert`,
`KeyPart`, `HashFind`, `HashLen`), `types.loft` (`Row.keys`, `flat`, `render`), `crt.loft` and
`shim/crt.c` (the key stack and four routines, marshalling only), `tests/selfhost.rs`
(`c_type_table` reads `loft_keys{tp}`).

**Cases** (`kernels/hashes.loft`, values by hand, value and leak and sweep asserted): a hash
field counting words (a hit updated in place, a miss added); a hash local whose equal keys

## The fourth slice, continued — walking a hash: BUILT 2026-10-30

**Census before it** (1 027 programs, 156 pass): 8 programs stop at `n_hash_sorted`, and 5 more
at `OpEqRef`/`OpNeRef` outside a walk (a placed call's "is the answer already in the buffer",
`if OpEqRef(___pans_1, __ref_1)`, and a loop's `p != null`).

**What a walk is, in the IR.**  `for c in h` takes a SNAPSHOT of the hash's elements in key
order, then steps over it:

```loft
for c in h { s += c.n; }
// _hash_scratch_1 = n_hash_sorted(h, <hash type>);            → loft_hash_sorted(h, keys, nk)
// c#iter_state = OpIterate(_hash_scratch_1, 132, 4, keys, 0, 0) → loft_scratch_iterate
// loop { c = { c#index += 1; OpStep(c#iter_state, _hash_scratch_1, 132, 4) }
//                                                               → loft_scratch_step(&state, …)
//        if OpEqRef(c, OpNullRefSentinel()) break; …body… }    → loft_ref_eq
// OpFreeScratch(_hash_scratch_1); _hash_scratch_1 = null; OpFreeScratch(_hash_scratch_1);
//                                                               → loft_free_scratch
```

The snapshot is two records claimed in the HASH'S OWN store (`loft_scratch_of`: a vector of
(record, offset) pairs and a header marked `0x5C4A`); the step reads the next pair still
non-zero, so an element removed during the walk is skipped.  A `return` out of the walk frees
the scratch before it returns (measured: the IR places `OpFreeScratch` on that exit too).

**The invariant is unchanged:** each operator is its runtime routine, marshalled by the shim;
loft reads only what the C generator reads in place (the reference compare).

| operator | interpreter op | runtime routine |
|---|---|---|
| `n_hash_sorted(h, tp)` | `HashSorted`, `a` = tp | `loft_hash_sorted(h, T[tp].keys, T[tp].nk)` |
| `n_hash_unsorted(h, tp)` (`unordered(h)`, a `par` walk) | `HashSorted`, `b` = 1 | `loft_hash_unsorted(h)`: slot order |
| `OpIterate(x, on, arg, keys, 0, 0)`, `on & 63 == 4` | `ScratchIterate` | `loft_scratch_iterate(x)` |
| `OpStep(state, x, on, arg)`, `on & 63 == 4` | `ScratchStep`, `a` = the state's slot, `b` = reverse (`on & 64`) | `loft_scratch_step(&state, x, reverse)` |
| `OpFreeScratch(x)` | `FreeScratch` | `loft_free_scratch(x)` |
| `OpEqRef`, `OpNeRef` | `RefEq`, `a` = 1 for `!=` | none: `loft_ref_eq`, read in loft as `OpRefIsNull` is |

Any other walk kind (an index, a sorted, a spatial) or a walk with key bounds is refused by
name (`a walk of kind N`, `a walk with key bounds`); those collections are refused earlier, at
their variable's kind, anyway.

**Ownership: nothing moves.**  The snapshot's records are claims of the hash's store, so whoever
owns that store owns them, and the scratch variable binds PLAIN: its store has an owner, so the
bind is a view (§ Ownership at run time).  `OpFreeScratch` releases claims inside a store, never
a store, so the owner table is not asked; the second `OpFreeScratch`, of the null sentinel, is
the runtime's no-op.  One edge: a READ-ONLY source gets its snapshot in a fresh store of its own,
which a plain bind would adopt and the null rebind would then free a second time.  The shim has
no read-only store (every store it holds was made by `loft_database`), so that edge cannot be
reached; the leak check is its falsifier if that ever changes.

**Two marshalling decisions.**
1. **The state crosses as a value and comes back in `out[3]`**: `crt::scratch_step(out, state,
   store, rec, pos, reverse)` writes the element's three parts to `out[0..3]` and the state the
   step leaves to `out[3]`; the run loop stores it into the state's slot.  The state is the
   runtime's `[lo, hi)` packed as `hi << 32 | lo`; it is loft's null only at `hi = 2³¹, lo = 0`,
   a snapshot of two billion elements.
2. **The walk routines move into `loft_hash.h`.**  `loft_scratch_iterate`, `loft_scratch_step`
   and the range helpers they use (`loft_iter_range`, `loft_iter_next`) are in `loft_keyed.h`,
   which the shim does not include (it carries the par threads, the paged loads and the
   renders).  They read only the snapshot `loft_hash.h` writes, so they move beside
   `loft_scratch_of` and `loft_free_scratch`, unchanged: a pure move inside the runtime, which
   every C program concatenates in the same order, `loft_hash.h` before `loft_keyed.h`.

**Code points:** `lower.loft` (`n_hash_sorted` routed to `store_call` beside the operators; the
four operator arms; `effect`), `run.loft` (the five ops), `crt.loft` and `shim/crt.c` (four
routines), `src/c/loft_hash.h` / `loft_keyed.h` (the move).

**Cases** (`kernels/hashes.loft`, values by hand, value and leak and sweep asserted):
1. A hash local walked and summed: keys `k0..k{n-1}`, `n` = i × 10; walk(4) = 60, walk(0) = 0.
2. Key order: names inserted `"b"`, `"c"`, `"a"`, concatenated in walk order: `"abc"`.
3. A walk over a hash FIELD (`bag_of(5)`, § the fourth slice's first case): the counts 2 + 2 + 1
   = 5 over 3 entries: 503.
4. A walk that writes through each element (`c.n += 1`), then a lookup reads the change: a view.
5. A walk left by `break` and one left by `return` (the first `n` over a bound); no leak, no
   sweep, and a second walk of the same hash afterwards still sees every element.
6. Two walks of one hash nested — two snapshots live at once: the pairs with `a.n < b.n`.
7. A walk of an empty hash: nothing visited.
8. `c#index` inside the walk: Σ index × n over `k0..k3` = 0 + 10 + 40 + 90 = 140.
9. `OpEqRef` between two live references (a placed call's buffer test) — the census's five
   programs are its cases; the walk's own test covers only the null side.
10. `unordered(h)`: the product of n + 1, which no order changes: 1 × 11 × 21 × 31 = 7161.

**Built.**  Every case passes on the interpreter, leak-free with nothing swept, and so does the
whole package on `--native-c` and `--native` (`LOFT_SELFHOST_BACKEND`, `tests/selfhost.rs`).
The `crt` package walks a hash through the shim alone, in key order, in reverse and in slot
order, on all three.  The falsification: a walk stepped in reverse fails `order(3)` on the
interpreter and on `--native-c`.  **Census: 1 027 programs, 158 pass, 0 leak, 0 wrong, 0
crash, none swept** (156 before).  Of the fourteen programs a walk stopped, two pass and the
rest stop at the next refusal: `OpAppendVector` 4, `OpVectorIsNull` 2, and one each of a sorted
local, a walk of a sorted field, `OpFormatDatabase`, `OpSizeHash`, `OpCastVectorFromText` and
`OpExpose`.  Refused next, by programs: `OpAppendVector` 61, function values 56, a `&` record or
vector 53, `n_write_bytes` 51, `OpFormatDatabase` 49, tuples 49, `OpDistinctStore` 32,
iterators 25.

**Design → code (walking).**  Transcribed directly, with one row added: `n_hash_unsorted`, the
slot-order snapshot `unordered(h)` takes, is the same snapshot stepped by the same routine, so
`HashSorted` carries it as its `b`.  The cases build each hash in place, because a hash bound
from a call is `OpReplaceKeyed`, which is not carried yet (4 programs).  The census runner, which
is the interpreter compiled through the C backend, then failed to build: the C generator

alone.  That is a C-backend defect on main, which answers silently wrong for a library's

## Appending a vector — `OpAppendVector`: paper design

**Census before it** (1 027 programs, 158 pass): 61 programs stop at `OpAppendVector`, the most
of any refusal.

**What it is, in the IR.**  `v += other` for two vectors, and a struct literal whose vector
field is given a vector local, both append ELEMENT COPIES:

```loft
out += [R { id: i, ins: ins }];
// OpAppendVector(OpGetField(_elm_3, 8, <vector<In>>), ins, <In>)   → loft_vec_add(T, In, v, ins)
// … ins is freed by the IR afterwards; out's element owns copies of its own
```

The runtime routine is `loft_vec_add` (`loft_rt.h`, which the shim includes): the elements'
bytes copied into `v`'s store (one block when they own no heap and fit), then, for an element
type that owns heap, each element's claims copied by the type table (`loft_copy_claims`).  So the
copy is the table's, as `OpCopyRecord`'s is, and the table is loaded first.

| operator | interpreter op | runtime routine |
|---|---|---|
| `OpAppendVector(v, other, tp)`, `tp` not linked | `VecAdd`, `a` = tp | `loft_vec_add(T, tp, v, other)` |

A linked element type is `loft_vec_add_array`, in `loft_keyed.h` (the shim does not include it),
and is refused by name (`an append of a linked element type`); `OpPrependVector`, which only a
rewrite emits and which stops no census program, stays refused.

**Ownership: nothing moves.**  The copies are claims of `v`'s store, which its owner already
owns; `other` keeps its store, and the IR frees it as before.  A self-append (`v += v`) is the
runtime's own case (`same_vec`: the source record is read again after the resize).

**Code points:** `lower.loft` (the arm, `effect`), `run.loft` (`VecAdd`), `crt.loft` and
`shim/crt.c` (`vec_add`, marshalling only).

**Cases** (`kernels/vectors.loft`, values by hand, value and leak and sweep asserted):
1. A struct literal's vector field from a local of records holding texts, the local freed after:
   the struct's copies read their own texts.
2. `a += b` for two integer vectors, `a` with room (the block copy) and `a` empty (a fresh claim).
3. `v += v`: the elements doubled, in order.
4. An append of an empty vector: nothing changes.
5. A vector of texts appended, then the source cleared: the appended texts survive.
