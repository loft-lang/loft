# @PLN91 strand 1b — phase S3, the store: paper design

A child document of [1b-interpreter.md](1b-interpreter.md).  Status: **DESIGN, for the owner's
review; nothing built.**  The direction is the owner's (plan § S3): the running program's
records, vectors and texts live in the C runtime's own stores, reached through `selfhost/crt`.

## Why S3 is next

The census (1 018 programs) passes 27 and answers none wrong; of the 987 it refuses, 663 stop at
a record (`TyReference`), 118 at a vector, 53 at a struct enum and 33 at a hash.  Every one of
them is a value the store holds.

## The invariant

**A value the interpreted program keeps in a store is a record of the C runtime's stores, laid
out by the image's type table, and only the C runtime's own routines read, write, claim, copy
or free it.**

The interpreter's loft code never computes an address, a size or a field offset of its own.  An
operator that names a field passes the field's byte offset from the IR (`OpGetInt(p, 8)`)
unchanged.  So the interpreter cannot disagree with a `--native-c` program about where a
field is or when a record is freed.

Where the invariant is asserted, and so where it can break:

1. **One `crt` routine per store operator**, each calling the runtime's routine of that
   operator: `OpGetInt` → `loft_get_int`, `OpSetText` → `loft_set_text`, `OpDatabase` →
   `loft_database_typed`, `OpFreeRef` → `loft_free_ref`, `OpCopyRecord` → `loft_copy_record`.
   The runtime already defines every one of these (`src/c/loft_rt.h`).
2. **One representation of a reference in the interpreter** (question 1).
3. **One type table** handed to the runtime (question 2).

## The stores are the shim's own

`loft_crt.h` includes the runtime's first three headers.  Their globals are `static`, so the
`crt` shim has its own copy of the runtime, and with it its own stores:

- Under `--interpret`, the shim is loaded as a library, and its stores are the only C stores in
  the process.
- Under `--native-c`, the interpreter itself is a C program with its own stores.  The shim's
  copy sits beside them, and the two never meet.

The interpreted program's data therefore never mixes with the interpreter's own: a
`loft_free_ref` in the program cannot release an interpreter record.  Probe P4 checks this
before anything is built on it.

## Question 1 — how a reference crosses a `#c` call — DECIDED (owner): its three parts

A reference is `{store_nr: u16, rec: u32, pos: u32}` (`loft_rt.h:1045`), 80 bits, and a `#c`
argument is a scalar of at most 64.  `pos` can exceed 16 bits: a reference to a vector element
is the vector's record plus `8 + i × size`.

**A reference is its three parts, as three integers.**  It is a new kind, `KRef`, held as three
adjacent slots on the integer stack, and every `crt` store routine takes `(store, rec, pos)`.
The parts map one to one onto `loft_ref`, so neither side packs or masks anything.  A null test
(`OpRefIsNull`) is `rec == 0`, read in loft.  `#c` takes up to 32 arguments (`c_call.rs`); the
widest first-slice routine, `loft_copy_record`, takes eight.

```loft
// the IR of `p.x += d`:  OpSetInt(p, 0, OpAdd(OpGetInt(p, 0), d))
crt::set_int(p_store, p_rec, p_pos, 0, crt::get_int(p_store, p_rec, p_pos, 0) + d)
```

Declined:
- **Two integers** (`store_nr << 32 | rec`, `pos`).  One argument fewer, but packing and masking
  on both sides of every crossing, and a mask written wrong gives a reference that is quietly
  wrong.
- **A handle table in the shim**, which keeps a second record of every live reference.
- **One 64-bit integer**, which limits `pos` to 16 bits and breaks silently past byte 65 535.

## Question 2 — the type table

`loft_copy_record`, the free of a record that owns texts or vectors, and every keyed
collection read a table of type descriptors (`loft_tdesc`: kind, size, fields with their
offsets, element type, keys).  A `--native-c` program has that table compiled in: the C
generator's `copy_table` (`src/c/mod.rs:825`) writes it from the program's store schema.  The
interpreter has the same schema, in the image (`Bundle.types`, `src/database/types.rs`'s
records), but no table.

```loft
struct Point { x: integer, y: integer, name: text }
q = p;      // OpCopyRecord(p, q, tp): the runtime copies `name`'s text because the table
            // says field 2 is a text at byte 16; without the row it copies 24 bytes and
            // `q.name` and `p.name` share one claim, so the first free leaves the second dangling
```

- **(a) The shim builds the table** from numbers the interpreter passes out of `Bundle.types`.
  This is a second writer of the same rows, in C, beside `copy_table` in Rust.
- **(b) The image carries the table.** `copy_table` is split so that it produces the ROWS once:
  the C generator formats them as C source, and `--emit-image` stores them in the image beside
  the IR.  The interpreter hands them to the shim, which only points `loft_tdesc` at them.  One
  writer, with two readers.
- **(c) The interpreter builds the table in loft** from `Bundle.types`.  This is a third writer.

**Recommendation: (b).**  The rows have one home, so a layout change reaches the C backend and
the interpreter together.  The image already carries what the compiler derived.

## The first slice — records of scalars and texts

What the census's smallest record programs emit (`introspect` of a three-field struct, a
constructor, a mutating call and a copy):

| operator | runtime routine | note |
|---|---|---|
| `OpDatabase`, `OpDatabaseNP` | `loft_database_typed` | a fresh record of a type |
| `OpGetInt`, `OpSetInt` (and the `Int4`, byte and short widths) | `loft_get_int`, `loft_set_int`, `loft_get_int4`, … | the width is the operator's |
| `OpGetText`, `OpSetText` | `loft_get_text`, `loft_set_text` | a text is copied out into the interpreter's text stack |
| `OpCopyRecord` | `loft_copy_record` | needs question 2 |
| `OpFreeRef`, `OpFreeRefIfDistinct` | `loft_free_ref` | |
| `OpRefIsNull`, `OpConvBoolFromRef` | none | `rec == 0`, read in loft |

Vectors, struct enums, hashes and the other keyed collections are later slices, each using the
same three assertion sites, and each sized by the census once the first slice lands.

## Probes before building (each can fail on its own)

- **P1** — `crt` claims a record, writes and reads an integer field through `#c`, and frees it,
  on `--interpret`, `--native` and `--native-c`.  Expected: the value written comes back, and
  the store is empty again afterwards.
- **P2** — a reference survives the trip through `(store, rec, pos)` at the edges: `store_nr`
  65 535, `rec` 2³² − 1, and `pos` past 65 535.
- **P3** — `loft_copy_record` with a hand-written row for `Point` copies the text into a claim
  of its own.  Freeing the copy leaves the original readable.
- **P4** — under `--native-c`, a record the shim frees leaves an interpreter record with the same
  record number untouched.  This checks that the stores are separate.

## Cases for the first slice (both backends, values computed by hand)

A struct built and read, a field written through a parameter, a copy that diverges from its
source, a text field set and read, a record returned from a function, a null reference tested,
and the census before and after.  Each kernel is written beside the S2 kernels, and the
expected values are written down before the run.
