## What changed today

The plan was re-cut around one objective (owner): **an interpreter in loft with no Rust code
and no rustc dependency, on the C runtime.**  [README.md](README.md) now states it, the one
rule (a reimplementation: same IR, bytecode, memory structures, semantics, and later the
same C — a difference from Rust is a defect, never a decision), and **§ The path**: six
stages, each gated by a byte-identical diff before the next starts.

1. Front end in loft (1a) — lexer, parser, scopes and types, the shared IR passes.
2. Interpreter complete (1b + strand 9) — byte-identical bytecode, every comparison layer.
3. C generator in loft (strand 12) — byte-identical C, every optimisation ported.
4. Bootstrap fixpoint — stage 2's C for itself equals stage 1's.
5. The tool and tooling in loft (strands 8, 11).
6. Rust retired (strand 10's leftovers, the rustc backend, every `src/*.rs`).

Also recorded: speed is outside the interpreter's scope — the C optimisation layer aims every
routine below 3× its rustc version (@C136); the libraries are nearly Rust-free (47 packages: 35
loft, 9 own C99, 3 on the C `net` component; Rust left: `plugin_runtime`'s crates, the bench
twins, the library CI's cargo build and rustc leg); open question 9 is how much of the C
runtime (allocator, keyed collections, text routines) stays C.

Built (commit `38ca42dc9`): the image carries each operator's class (`op_hot` / `op_cold` on
`Definition`), and `LOFT_TRACE_BYTECODE=<file>` writes the opcode table and a hash per
function — the opcodes and bytecode layers of [1b-compare.md](1b-compare.md), for stage 2.
