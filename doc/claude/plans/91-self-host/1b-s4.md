# @PLN91 strand 1b — phase S4, keyed collections and their walks

A child document of [1b-interpreter.md](1b-interpreter.md).  Status: **two slices BUILT** on all
three backends — sorted, ordered and index (the first), spatial index and trie (the second).
Linked groups (`@FR-Col-Group`) and a group's index are the next step.

## The invariant

S3's, unchanged ([1b-s3.md](1b-s3.md) § The invariant): **a keyed collection the interpreted
program keeps is a record of the C runtime's stores, laid out by the image's type table, and only
the C runtime's own routines file, find, walk, remove or free its elements.**  The interpreter
names the routine the C generator names for the same operator and kind (`src/c/body/keyed.rs`),
hands it the collection's key parts from the loaded type table, and computes no position, order
or tree link of its own.  No owner decision was open: the hash slice of S3 already settled how
a keyed operator reaches the runtime, and S4 widens it by kind.

## How a keyed operator is carried

- **The kind travels with the op.**  The type table does not tell a sorted from a vector (both
  are laid out as one), so the lowering names the kind (`keyed_kind`: 1 sorted, 2 ordered,
  3 index, 4 spatial, 5 trie) and the shim switches on it.
- **Keys are the table's.**  A lookup's or a keyed write's parts go onto the shim's key stack, as
  the hash slice pushes them (`key_parts`); a walk's key list comes from its `OpIterate`'s `Keys`
  node, one `WalkKey` at a time, then its bounds' parts.
- **A walk's state is an integer**, as `loft_*_iterate` answers it; `OpStep` reads and writes it
  in its slot.  A spatial or trie walk is a snapshot (`n_radix_sorted`, `n_spatial_range`,
  `n_trie_prefix`) walked as a hash's is.

| operator | routine, by kind | guard |
|---|---|---|
| `OpNewRecord` / `OpFinishRecord` | `loft_sorted_new` / `loft_sorted_finish`; `loft_entry_new` with `loft_ordered_insert`, `loft_ix_insert`, `loft_rx_insert_record` | `kernels/keyed.loft` (all four) |
| `OpGetRecord` | `loft_seq_find` (sorted with the element size, ordered with 0), `loft_ix_find`, `loft_rx_find` | `keyed.loft` |
| `OpSetKeyed` | `loft_set_keyed` with the kind's `LOFT_KEYED_*` | the census |
| `OpHashRemove` | `loft_sorted_remove_owned`, `loft_ordered_remove`, `loft_ix_remove`, `loft_rx_remove_owned` | the census |
| `OpIterate` / `OpStep` (kinds 1–3, with key bounds) | `loft_ix_iterate` / `loft_ix_step`, `loft_seq_iterate` / `loft_seq_step` | `keyed.loft` `sorted_walk`, `index_walk` |
| `OpRemove` (`e#remove` in a walk) | `loft_vec_walk_remove` / `loft_array_walk_remove`, `loft_ix_walk_remove`, `loft_sorted_walk_remove`, `loft_ordered_walk_remove` | `sorted_walk` |
| the snapshots `n_radix_sorted`, `n_spatial_range`, `n_trie_prefix` | `loft_radix_sorted`, `loft_spatial_range`, `loft_trie_prefix` | `spatial_find`, `trie_find` |
| `OpLengthSorted`, `OpLengthIndex`, `OpSizeIndex`, `OpLengthSpatial`, `OpLengthTrie`, `OpSizeSpatial` | the vector's length; `loft_bt_len`, `loft_bt_table_bytes`, `loft_rx_count`, `loft_rx_table_bytes` | the census |
| a keyed local's empty literal | minted as its type, named `sorted<C[k,-k2]>` (or `ordered<…>`), `index<…>`, `spatial<C[x,y]>`, `trie<C[w]>` as `Stores` names them | the census |

**Measured** (2026-11-01): the census went from 720 to 766 programs passed over these slices and
the store natives beside them ([1b-s3-operators.md](1b-s3-operators.md)).

**Design → code.**  Two findings on the way, fixed where they lived: the shim appended to a null
text local as if it were empty, where `loft_text_concat` (and the Rust interpreter) keep a null
accumulator null and a null source makes it null (`@FR-E-NullArg`); and a `#cwd` program could
not be run from its image, which did not record it — the IR's `Bundle` carries `cwd` now, and the
runner, itself `#cwd`, leaves the anchoring to the shim.
