## Owner rulings this session

- **Write what you want; choose how it is handled after the fact** — like adding an index to an
  existing store.  A representation (set, index, hash) is an annotation or a later decision,
  never a rewrite of the code that uses the data.  The two rulings below are cases of it.

- **No map-typed hashes.** `hash<T[k]>` is an index on a record's key fields and its spelling
  teaches that; a map or a set is not a looser `hash`.  A set (the elaborator's `const` name
  lists read with `.contains`) would be a type of its own, `set<T>` — no subscript, no writes
  through an element, idempotent insert, set algebra — whose representation is HIDDEN: the
  compiler picks it from the set's use (a constant membership test: a perfect hash or a switch;
  membership-heavy: a hash; iterated: ordered — walking a hash's table loses what it buys).  Its
  iteration order belongs to the type, so the choice never changes an answer.  Refined: a set is
  an ANNOTATION on a vector — the vector's syntax unchanged (literal, `.contains`, iteration,
  `s[i]`, `len`), set algebra the only addition — so its order is the vector's insertion order and
  its representation the vector plus a hidden membership index (none, a perfect hash for a
  constant, a hash index).  Still to settle: uniqueness on insert (it changes `len`), writes by
  position (refuse or re-check), removal by value against by position.  On a CONSTANT the
  annotation limits what is allowed: reads only (membership, iteration, `len`, set algebra into a
  new value), a duplicate in its literal refused at compile time, the representation the fastest
  fixed one — so a first slice is constant sets alone (the elaborator's name lists), and the
  mutable-set questions wait for a consumer that needs one.
  Before any new type: `CONST.contains(x)` scans (≈1.3 µs for 30 names on the interpreter,
  against ≈0.4 µs for the `||` chain it replaced in `text_dest_call`); the compiler knows the
  constant's contents and can lower that call itself.
