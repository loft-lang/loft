# @PLN179 — execution modes for a script: interpreted, compiled, optimised — and where the artefact lives

The owner's question (2026-09-30): a dual mode for scripts — the interpreter version, and an
automatically compiled, optimised version stored in git for real performance — and whether
every script gets it or only the long-running ones.  This is the evaluation; the plan that
owns it is [README.md](README.md).

## What exists already

The dual mode is not a design to make, it is the language's steady state
([C71](../../DESIGN_DECISIONS.md)): one source, three tiers, and a cache that picks.

| tier | flag | what it is | start-up, installed binary (PERFORMANCE.md § N6) |
|---|---|---|---|
| interpreted | `--interpret` | no rustc, ever; the iteration mode | ~2 ms |
| native | `--native` (the DEFAULT) | rustc without `-O`: a fast compile, ~6× slower code than release | ~7 ms warm; a cold miss pays the compile |
| release | `--native-release` | `-C opt-level=3 -C codegen-units=1`: what ships | ~7 ms warm; a longer compile |

The compiled artefact already has a home: `<dir>/.loft/cache/<name>-<source hash>/`, keyed
on the SOURCE (@PLN166 B3) in front of a key on the generated Rust, invalidated by a source
edit, a stdlib edit, a rustc or loft version change (`tests/native_source_key.rs` is the
falsifier).  A warm hit spawns zero rustc processes (N6, `strace`-verified).  So "the
interpreter version and an automatically compiled version" is what `loft x.loft` does today:
the first run compiles, every run after it runs the binary, and `--interpret` is the same
source without the compile.

## Measured on the census script — installed binary, idle box, 2026-09-30, three runs each

| run | wall |
|---|---:|
| `--interpret` | 4.5–4.7 s |
| `--native` (the default), warm cache | 1.1–1.2 s (first run 2.2 s: the cold compile) |
| `--native-release`, cold (compile + run) | 3.4 s |
| `--native-release`, warm | 0.41–0.47 s |
| the `hello` script: `--interpret` / default warm / Python / bash | 15–22 / 32–37 / 15–19 / 5 ms |

So on a real script native is ~4× the interpreter, release ~10× (2.6× native), and a cold
release compile costs ~3 s — it pays for itself after four runs of this script and never for
a script that runs in a millisecond.  On start-up the interpreter is AT Python's bar and the
warm native path is twice it (REASONS.md row 1).  The cache entry for the census is 1.8 MB;
the `tests/scripts` entries are 10–13 MB each (34 of them, 431 MB).

Two measurement traps, both already in PERFORMANCE.md: `LOFT_TIMEOUT` makes the native
checkpoint take a lock on every call (~2× on call-heavy code — `loft test` pays it), and a
from-source `target/release/loft` runs with the program cache OFF (rule 4), which is why
the 78–84 ms start-up in REASONS.md row 1 is not the installed number.

## Store the compiled version in git?  No — and here is the arithmetic

| cost | size |
|---|---|
| one artefact | 1.8 MB (a script) to 13 MB (a test program) |
| platforms CI runs | 3 (Linux, macOS, Windows) — a binary is one of them |
| the population | 231 scripts |
| one full generation | 231 × ~5 MB × 3 ≈ **3.5 GB**, kept in history for ever |
| when a generation goes stale | every loft release and every rustc bump (the key includes both), i.e. weekly — plus every edit to the script |

Against that, the artefact carries nothing a reviewer can read, nothing a diff can show,
and a supply-chain question the registry answers for libraries with a signature
(RELEASE_PUBLISH.md) and git cannot answer for a blob.  The repository commits exactly one
built binary today (`doc/pkg/loft_bg.wasm`, 7 MB, one platform, regenerated by a gate that
knows when it is stale — GALLERY_CI.md), and that one is a deliverable, not a cache.

**What carries the performance instead, each already the repo's own mechanism:**

1. **The source-keyed cache is the store.**  Per checkout, self-invalidating, zero rustc on a
   hit.  Nothing to commit, nothing to go stale unnoticed.
2. **CI warms it the way CI already warms the rlibs** (CI_BUDGET.md): an actions cache keyed
   by loft's sha, the rustc version and the script's hash — each script compiles once per
   change across runs instead of once per run.  Without this, CI pays ~3 s × the scripts it
   runs on every leg; with it, only the scripts a PR touched.
3. **A hook never compiles.**  The edit hook and the commit hook run `--interpret`: 2 ms
   start-up beats any warm binary and there is no rustc in the loop of a save.
4. **A script that ships to users is a release artefact**, built per platform by the release
   bundle (RELEASE_PUBLISH.md) — that is the one place a precompiled script belongs, and no
   script in this repository's tooling ships.

## All scripts, or only the long-running ones?  Decided by the twin, per script

The number that decides is the script's own run time against its compile cost, and the twin
(strand 2) measures both sides on every port, so the choice is read off the scoreboard rather
than guessed:

| the script's warm run | mode | why |
|---|---|---|
| under ~100 ms (a hook, a one-line check, a stamp) | **interpret** | native gains nothing measurable and a cold miss costs 2–4 s on every edit |
| ~100 ms to ~1 s (most reports) | **native** — the default, cached | the 3.5× is real and the dev-tier compile is short |
| over ~1 s, or run in a loop / in CI on every leg (the census, the audits, the checklist) | **release** | 2.4× over native; a ~3 s compile amortised in four runs |

So: every script gets the compiled version by default (that is what `loft` does), the short
ones opt OUT, and the long ones opt UP.  The declaration has to live in the script, because
a Makefile line or a workflow step is exactly what the port removes: today the only file
directive is `#cwd` (`src/parser/mod.rs`), so **a `#mode interpret | native | release`
directive is a gap for strand 3** — one line at the top, read by `loft` before it picks a
backend, overridable by the flag.  The census gains a `mode` column, and a script whose
declared mode disagrees with what its twin measured is a scoreboard row, not a mystery.

## What this does NOT change

The bar (README § The bar) is measured on the mode the script declares, against the
original as it runs — a Python script has no compile step, so a loft script that needs one
on first run must still beat it on the runs that follow, and the twin reports both the
cold and the warm number.
